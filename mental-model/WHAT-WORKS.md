# What works

What is live-proven in FontLab, and which version each feature needs. An entry is added only after a live run; what is stub-tested only is named as such. What is not proven or not built, and what comes next: [CURRENT-STATUS.md](CURRENT-STATUS.md). This file is not a startup core file: [AGENTS.md](../AGENTS.md) says when to read it. Word budget: 3,000 ([MARKDOWN-MAP.md](MARKDOWN-MAP.md)).

## Live-proven in FontLab

The areas follow the summary table in [CURRENT-STATUS.md](CURRENT-STATUS.md).

### Reading

- **Reading:** outlines with element transforms (scale, offset, slant), cubic and quadratic outlines, Power Brush output, widths, sidebearings, the stale-view fallback; since 0.120 / 0.42 a glyph with modern nodes from the modern layer only, its transforms applied, checked horizontally (497–520); since 0.121 / 0.43 checked vertically too, against FontLab's `inkBox()`, and quadratic outlines from their exact extents (INK 521–533, V121 534–541); since server 0.46 open contours, straight and cubic, `verified` with an `svg_path` without Z and no direction (OC 579–585). → [topics/reading.md](topics/reading.md)
- **Components, partly** (one master, 606–656): one component, identity, offset and horizontal scale read `verified`; two components in a glyph and one source shared by two glyphs read correctly (627–636). Since 0.128 / 0.49 `get_glyph_outline` labels a component and names its source (624–626). Since 0.130 / 0.50 an accent inside its base reads `verified` element by element (652), and a component found behind its source reads `unverified` (651, 653; plain offsets only). Rotation, 90° and 30°, set in FontLab's Transform panel, reads `verified`, a rotated curve with its exact extent (768–771). Not proven: mirroring, slant, vertical scale, a rotated component inside another, other masters. Components are placed by `add_component` (below), through FontLab's recipe build (`recipe`, `autoLayer = True`, `buildAuto()`, then `autoLayer = False`), which a research probe first showed giving a normal component (1041b–1042b, one run each). → [topics/reading.md](topics/reading.md)

### Writing and editing

- **Writing:** create and delete glyphs (name safety rules), Unicode set and clear, width, sidebearings, closed straight and cubic contours into an empty glyph, since 0.126 / 0.47 open ones too, alone or with closed ones (OT 595–603), though FontLab's export (TrueType and OpenType PS) drops open contours without a warning (EX 779–791), auto sync after every modern write, also with the glyph's editor tab open (T3, 257) and on an existing glyph with a legacy layer, in a font opened from a file (T4, 145a–g, 259, 260: a plain contour and a Power Brush shape). → [topics/geometry.md](topics/geometry.md), [topics/names-unicode.md](topics/names-unicode.md), [topics/fonts-and-sync.md](topics/fonts-and-sync.md)
- **Editing an existing outline: `move_nodes`** (listener 0.154 / server 0.64 and 0.65, MN 1016–1025, one run each, one master, Demo mode): moves of on-curve nodes and cubic control points, one or several per call, read back `verified`, with the sidebearings computed from the nodes while FontLab's own values lag (shown apart); a smooth node moved without its handles and a component are refused and nothing moves; also on a contour drawn in FontLab's GUI. Not proven: the refusal of several shapes, a Power Brush glyph or an element transform (stub only), quadratic outlines. Edit > Undo lists the move but does not revert it (1023); since server 0.65 the reply's `undo_note` says so (1025). → [topics/geometry.md](topics/geometry.md)
- **Placing a component: `add_component`** (listener 0.169 / server 0.66, AC 1079–1101, one run each, one master, Demo mode): one component of a glyph of plain contours into an empty glyph, at (0, 0) and at an offset, read back `verified`; refusals change nothing; the font in front is used with two fonts open; its mark alone brings FontLab's save question (1097–1101). Since 0.174 / 0.68 the `components` list (AC2 1178–1215; the list form 1180–1213): 2, a repeated source, 15 at mixed offsets and a dotted name `verified`, the width restored; above 30 the person is asked first; refusals change nothing. Limits: since 0.175 / 0.69 a list with an underscore source name is refused with nothing changed, since FontLab's recipe of several glyphs reads `a_b` as a ligature of its parts (1234; AC3 1237–1239), and the single form still places such a glyph (1238); since 0.178 / 0.71 the single form writes the width back too, which before it left at FontLab's value (1250a; CC 1254, 1255); Edit > Undo offers nothing (1090); `remove_component` (0.179 / 0.72) removes them, live RC 1258–1264b: one, a list, all of a glyph, 30 in one call, one beside a contour, with two fonts open; a wrong source or offset refused with nothing changed; the auto-layer refusal stub-tested only (researched, RM 1241–1245); an empty target, a plain source, one master; two recipe-built components once became contours, unexplained (1059). Since 0.186 / 0.73 a target that is not empty (`placement` "temporary layer"), live NB 1347–1352, one run each, one master: the single form beside a contour, a component and a Power Brush stroke, the list form (three, a repeated source) beside a brush and a contour, all `verified` with the old elements kept first, unchanged after a later `create_glyph`; a second layer refused with nothing changed. Since 0.187 / 0.74 every target needs exactly one layer, the active one: a glyph with two layers refused with either active, nothing changed; one-layer targets, empty and not, still placed (1354–1358a, one run); the list form likewise, and its one-layer and underscore refusals on a target with content change nothing (NB3 1360–1363a). Not run live: the restore after a failure, the auto-layer refusal, two fonts. → [topics/reading.md](topics/reading.md)

### MCP clients

- **ChatGPT Desktop** (2026-11-18, listener 0.187 / server 0.74, one run, Demo mode, not a numbered live test): set up through `config.toml` ([RUNBOOK.md](RUNBOOK.md) step 4b), in Work mode and in Codex mode it called `fontlab_status`, `list_glyphs`, `create_glyph`, `draw_polygon`, `set_glyph_width`, `get_glyph_outline` and `finish_changes`, created six glyphs with outlines in an unsaved font and ended with the bold save reminder. A plain chat has no Glyphbridge tools and offers to continue in Work mode. Other tools, the Settings route and macOS untested.

### The save question and saving

- **Save reminder:** `finish_changes` through the Desktop chat (T2, 253–255): one request with three verified writes ended with one bold reminder, a read-only request with none; FontLab showed LSB 50, width 400, RSB 50 as reported.
- **Save question** (S1, 657–691c): since 0.132 / 0.51 a verified, synced glyph write turns FontLab's changed icon blue: `create_glyph` (668, 669), width, sidebearings, `draw_polygon`, `draw_path` and Unicode (677–681). Since 0.133 / 0.53 a verified delete does too, through one surviving glyph (688). FontLab's question on close was seen after every one of these (668, 669, 682, 688, 698–701). On a Power Brush glyph, width, sidebearings and Unicode turned the icon blue and kept the brush and its fractions (693–695). With two fonts open, five glyph writes marked only the font in front (702–706). Since 0.134 / 0.54 a `set_kerning` that changed an entry is marked through a glyph of a changed pair, and FontLab asked (718, 719); before 0.136 / 0.56 the icon usually needed a hover there (719, 722, 723, 725, 726), and since then it went blue at once (748–753, [DECISIONS.md](DECISIONS.md)). Not marked: a delete that leaves only `.notdef` (689), `create_glyph` with no layer (691a). → [topics/server-and-endpoints.md](topics/server-and-endpoints.md) §2
- **Save and reopen** (707–712, one master, a font made with File > New Font): saved at FontLab's question and reopened, tool-made plain glyphs came back exactly: nodes, widths, sidebearings, Unicode. A Power Brush glyph kept its advance, offset, Unicode, node count and brush element, but nearly all its nodes changed by under one unit at load, also on a glyph no tool wrote to. Open contours drawn by `draw_path` or with the Pen tool came back with the same nodes and `closed` flags, `verified` (755–764). A font made by `flPackage()` came back the same way (772–778). The brush fractions come from FontLab rebuilding the outline from the stroke at load (PB 792–799 `.vfj`, PB2 809–812 `.vfc`); the brush size changes them (820). FontLab's panels show sidebearings rounded down (PB2 820, 827). → [topics/reading.md](topics/reading.md) §8p, [topics/geometry.md](topics/geometry.md) §8g

### Kerning

- **Kerning** (K1–K14 and K16, 2026-11-01 to 2026-11-03, each test in [LIVE-TESTS.md](LIVE-TESTS.md)): **since 0.104 / 0.33** `get_kerning` reads the current master's table and reports each value's `source` (live 219–223); with several fonts open it reads the font in front, matched by path, and names it (0.112 / 0.37, 265–268). Proven: GET and POST, the agent reading only the pairs it needs and asking above 250, `text` mode equal to the KERNING panel with its special characters, errors never read as zero, an exception winning over its class, a FontLab text line and Arial's `kern` feature agreeing with the table, an empty table, timings up to 2,000 pairs. → [topics/kerning.md](topics/kerning.md) §10, §11
- **Kerning writes:** `set_kerning` writes glyph : glyph pairs of the current master, in whole units, verified by a re-read and saved like GUI pairs (research 542–564, live 565–577). Since 0.136 / 0.56 a write that changed an entry asks FontLab to refresh its KERNING panel, which then showed new pairs and new values at once (744, 745), with two fonts open (747, one run) and in a freshly started FontLab (748); the changed icon went blue at once in 748–753, with no hover. Without that call the panel shows them only after a switch to another font and back, or a save and reopen. Classes, other masters and large fonts are untested. Before 0.134 / 0.54 closing asked no save question and lost them (561, 562), since then see the save question above; Undo cannot take them back. → [topics/kerning.md](topics/kerning.md) §13, §14
- **Kerning groups:** since 0.190 / 0.75 `get_kerning_groups` reads the current master's kerning groups with their side, members and id, cross-checked with FontLab's class list (KGL 1376–1379, one run each): every group, named groups, the groups of a glyph, an unknown name and an OpenType class as errors for that name only, and a Classes-panel edit seen at once. One font, one master; the 250-group approval, a mismatch and several fonts are stub-tested only. → [topics/kerning.md](topics/kerning.md) §15
- **Removing kerning pairs:** since 0.192 / 0.76 `remove_kerning` removes glyph : glyph entries of the current master, verified by a re-read (RK 1398–1402, one run each): an exception over a class removed, with the class value that applies again; pairs with no entry reported, the others going on; the KERNING panel updated at once. One font, one master; the save question for a removal alone (Demo mode), Edit > Undo, several fonts and the 250-pair approval are untested live. → [topics/kerning.md](topics/kerning.md) §16

### Fonts

- **No font open** (P0.2): with the only font closed in a running FontLab, `fontlab_status` gave `font_open: false`, and a width read and a create were refused; Arial reopened read as before (227, 228). In a freshly started FontLab (K13, 244) all 8 read routes answered `open: false`, the placeholder glyph `Paper` included, with no dialog. Not seen live: the other write tools (stub only). → [topics/fonts-and-sync.md](topics/fonts-and-sync.md)
- **Several fonts open** (T5, 262–331): every tool of that time follows the font window in front, every reply names its font, and a switch is reported in the next reply, also after an error; `get_kerning` refuses an unsaved font in front. Later tools: `set_kerning` with two fonts (747), `create_font` beside one and two (916, 917), `add_component` with two (1091–1095); `move_nodes` not run with several. With three fonts, `draw_path`, the later tools but `create_font`, and the reads other than `list_glyphs` and `get_glyph_width` are untested; `get_kerning` is proven only in refusing an unsaved font in front (268). → [topics/fonts-and-sync.md](topics/fonts-and-sync.md)
- **Font names** (291–302): FontLab keeps the names Font Info shows in the font package (`psn`, `ffn`, `tfn`, `tsn`, `sgn`); the legacy `font.info` the tools read before can disagree (298). Since listener 0.118 `/font/current` reads the package when it is matched to the font (302), and says why when it is not (301); `get_current_font` reports them since server 0.41 (303). The delete dialog names the client as sent and the font, and the save reminder uses the system's shortcut (0.114 / 0.40, 304–308, [CHANGELOG.md](CHANGELOG.md)). → [topics/fonts-and-sync.md](topics/fonts-and-sync.md)
- **Names, their display and the save question** (894–914, listeners 0.144 / 0.145, one run each, FontLab in Demo mode, nothing saved): a name written through the API reads back and shows in Font Info, but the tab title and often the FONTS panel keep the old text; the tab follows only a Full name changed to a different value in Font Info (902, 907b), and typing another name, then the wanted one, works (910). `flPackage.title_name` returns the live Full name and changes nothing (905, 908). A name written through the API leaves the font unmarked, and it closes without FontLab's question (911); the package-level `notifyChangesApplied(title, <flPackage>, False)` brings the question back on a GUI font (912), on a `flPackage()` font named in its creation request (913), and on only that font with two others open (914). → [topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8k
- **`create_font`** (CF 915–920, listener 0.146 / server 0.60, one run each, Demo mode, nothing saved): unnamed with no font open ("Unnamed"), unnamed again in the same listener run beside it ("Unnamed1"), and named beside two fonts ("GBtest917", tab and FONTS panel at first "Unnamed2"); each reply agreed with FontLab, and every note showed in the OUTPUT panel. On close FontLab asked only for the named, marked font, in its live Full name; the untouched unnamed ones closed silently. Since listener 0.150 the new font is confirmed in front by `fgId` (932). Not run live: a family at the length limit. → [topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8k
- **A new font's first glyph with other fonts open** (PK 932–936, listener 0.150 / server 0.62, one run each): with two fonts open, `create_glyph` gave the first glyph its layer (`Regular`, `package master`) and the save mark, in a font made by `create_font` and in one already open, and `draw_path` read back `verified`; one font open works as before. Not run live: three fonts; `set_glyph_width` or `set_glyph_sidebearings` as the first write. → [topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8k
