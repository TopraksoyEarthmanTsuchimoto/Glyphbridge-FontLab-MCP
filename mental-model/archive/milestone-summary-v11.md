## 0. Design rule

Built after abandoning an unreliable third-party server that reported false successes. So: every failure gets a specific, honest
message; no write is reported successful unless the listener re-read the state afterwards; coordinates are called `verified`
only when FontLab's own numbers agree; **a failed read is never reported as "empty", "missing" or "none"**; a reply that could not check something says so
(`unknown`, `unreadable`, "could not check whether another glyph holds it") instead of staying silent.

## 1. Architecture and environment

Two processes over local HTTP (`127.0.0.1:8765`, never exposed):

1. **`glyphbridge_fontlab_mcp_listener.py`** (the FontLab-side companion of the MCP server; it does not speak MCP itself) runs *inside* FontLab's embedded Python 3.11.3, started by hand from the Scripting panel each
   session. Reports **raw FontLab facts only**. No background thread is possible (threads get no CPU while FontLab idles in its Qt
   loop): a `QTimer` polls a non-blocking socket every 25 ms on the main thread, so every `fontlab` call runs on the main thread.
   `QMessageBox` import: try `PythonQt.QtGui`, fall back to `PythonQt.QtWidgets`.
2. **`glyphbridge_mcp_server.py`** is a normal MCP server (SDK v2, `mcp>=2,<3`; 2.2.0 confirmed) in its own venv, launched by Claude
   Desktop over stdio. Never touches `fontlab`. All interpretation (curve rebuild, transform maths, verification, name rules, Unicode instructions) lives here.

Machine: Windows 11, venv Python 3.14, FontLab 8.4.2.8950. FontLab runs `C:\Users\<user>\Documents\FontLab\FontLab 8\Scripts\glyphbridge_fontlab_mcp_listener.py`
(a copy is kept in the project folder for the tests). Server, venv and `tests\`: `C:\Users\<user>\Glyphbridge-FontLab-MCP\`.
Claude Desktop config `%APPDATA%\Claude\claude_desktop_config.json` (the entry name `glyphbridge-fontlab` and the server name
`"Glyphbridge FontLab"` in the code were deliberately NOT changed by the rename):

## 4. How a glyph is read

| `kind` | meaning |
|---|---|
| `Move` | first on-curve node of a contour (this separates contours) |
| `On` | on-curve; an `On` right after an `On` is a straight line |
| `Curve` | cubic handle: exactly two between on-curve nodes |
| `Off` | quadratic off-curve point: runs of any length, implied on-curve at midpoints |

`smooth` matters only on on-curve nodes. One "To TT Curves" turns a cubic contour into the quadratic pattern (<= 0.63 unit deviation).

**Element transforms.** A FontLab *element* (shape) carries its own transform. `layer.findNode(i).x/.y` returns element-LOCAL
coordinates; FontLab's bbox, margins and drawing include the transform. The true transform is a Qt matrix per shape:
`x' = m11*x + m21*y + dx`, `y' = m12*x + m22*y + dy` (a 10 degree slant arrives as `m21 = 0.176327`).

**Verification statuses** (`get_glyph_outline` tries the direct route first):
- **`verified`** (`transform_source` "FontLab's own element transform, read directly"): real matrices applied; the result reproduces
  FontLab's control-point bounding box and left/right margins (tolerance 0.05 each).
- **`calibrated`** (fallback): matrices unavailable; transform estimated per axis from FontLab's bbox (scale + shift), confirmed by
  the horizontal margin. Assumes one element, no rotation/slant.
- **`unverified`**: something could not be confirmed; `x`/`y` are then RAW element-local values, the failed attempt is stored as
  `attempted_calibration_NOT_applied`, and `coordinate_space` says which space the numbers are in.
- With a transform applied, nodes carry `raw_x`/`raw_y` beside `x`/`y`. A mirrored glyph cannot pass the fallback as "verified".
- **Stale-view cross-check (server v0.25):** on the LEGACY route (the glyph has been opened in an editor, so the legacy view sees its nodes) a `verified` / `calibrated` result adds `verification.modern_margins_check` = `{status: agrees}`, or `{status: mismatch, differs, legacy, modern}` together with `status: unverified`, `stale_legacy_view: true` and a note; `{status: not_checked, reason}` when the extra read failed (the old verdict is kept and a note says so). Section 8i.

Verified live earlier, all `verified`: identity, scale + offset, 10 degree slant, cubic, quadratic, a Power Brush outline.

## 5. Layers

- `bodyLayer`/`activeLayer` (after the warm-up) hold the nodes; `glyph.layer` and `glyph.bodyLayerStrict` return a **placeholder
  layer named `Body` with 0 nodes for every glyph seen**, so a 0 from the `strict`/`glayer` routes proves nothing. Modern
  `flGlyph.bodyLayer` is `None` (use `activeLayer`).
- `layer.countContours()`, `countNodes()`, `countShapes()`, `len(layer)` match FontLab's GUI tooltip counts. `len(glyph.layers)`
  works (`fgLayers`): 1 for ordinary glyphs, **0 for a glyph with no outline data at all** (section 7).
- Multi-master / multi-layer glyphs are untested.

## 6. The legacy-to-modern bridge and its leak

`fontlab.flGlyph(fgGlyph, fgFont)` returns the real modern glyph for any glyph by name. Path used: `flGlyph.activeLayer.shapes` (a
REAL Python list, indexable) -> each shape's `.transform` (`QTransform`: `m11 m12 m21 m22 dx dy`). `flGlyph.fgGlyphId` equals the
legacy `fgGlyph.id`. `flWorkspace`/`flGlyphInfo` reach only the glyph open in the editor.

**Leak (measured):** each construction leaves one native reference behind (cause not isolated). Mitigation: ONE cached wrapper per
legacy glyph id, validated before reuse (name, `fgGlyphId`, `isValid()`), rebuilt if stale, cache cleared when the font path
changes (`elements.wrapper` reports `cached`). `release()` was deliberately NOT tried (crash risk).

## 7. `.notdef` check and warning dialog (v0.46 / v0.10)

**Why:** every font must have `.notdef` as glyph 0; the OpenType spec recommends a visible outline (rectangle, with or without a
question mark or X). A new FontLab font starts with an EMPTY `.notdef`: empty is valid, a normal state for a font in progress,
but not recommended. Agents must expect `.notdef` in every font and must never treat an unreadable one as empty.

**Detector** (`check_notdef()` in the listener, read-only; status on **positive evidence only**):

| status | rule |
|---|---|
| `missing` | no glyph named `.notdef` (evidence names glyph 0) |
| `empty` | exactly 0 layers and 0 components; or exactly 1 readable body layer with 0 nodes, contours, shapes and 0 components |
| `has_outline` | any node, shape or component |
| `unknown` | no verdict: `len(glyph.layers)` unreadable, 2+ layers, layer unreachable although it exists, any count not a plain number. **Never triggers a dialog** |

`.notdef` not at index 0 only adds a note. Fonts without a glyph named `.notdef` are reported `missing` even if glyph 0 is differently named.

**Dialog:** `POST /font/notdef/warn` re-checks inside the listener (never on the caller's say-so) and shows a modal
`QMessageBox.Information` with an OK button (title "Glyphbridge: .notdef glyph"; wording in `_NOTDEF_DIALOG_TEXT`, one text for
`empty`, one for `missing`, plus a line saying it is shown once per font per session). At most once per font **path** per listener
run (`_NOTDEF_WARNED`); `force: true` repeats it. Fonts with an empty or shared path share one memory slot. While the dialog is
open the listener answers nothing else: live-verified (a plain `/health` request timed out after 5 s while the dialog was open), so a second
request cannot stack a second dialog. Live-verified through Claude Desktop: the host tool call simply waits for the click, even for 90 s.

**Triggers (server):** `get_current_font` (automatic, adds a `notdef` entry), `get_glyph_outline(".notdef")` when it comes back
empty (adds `notdef_check`), and the explicit `check_notdef` tool. NOT `list_glyphs`, NOT other glyphs. Automatic checks are
best-effort: a failure becomes `{"status":"check_failed"}` and never fails the host tool. Results carry an `agent_instruction`
(tell the user in chat too; "unknown" -> say nothing about missing/empty).

**Error wording:** an outline whose layer cannot be reached says "this does NOT mean the glyph is empty"; for `.notdef` it also
points to `check_notdef`.

**Real-FontLab evidence (read-only probes, then live runs):**
- An empty `.notdef` (GUI shows it blank): `len(glyph.layers)` 0, `bodyLayer`/`activeLayer` `None` on every attempt, on every outline call (body
  and active routes) and on 3 of 3 later `layerstats` calls; one earlier layerstats success was never explained or reproduced. `hasBody` is a callable (never called).
- A drawn `.notdef` (checked on Arial opened from the system, 4548 glyphs): 1 layer, 2 contours, 8 nodes, 1 shape, 0 components,
  reads normally, status `has_outline`.
- `len(glyph.components)` is readable on the layerless `.notdef`; `GET /font/notdef` -> `empty`; `POST /font/notdef/warn` -> the
  dialog appeared (reported by the user) with `dialog_shown: true`; a second call -> `already_warned: true`, no dialog;
  `--check --notdef-warn` and `--check --outline .notdef` behaved as designed (`empty: true`, "no layer at all" note, `notdef_check`).
- **Through Claude Desktop** (v0.46 / v0.10): asking for the open font ran `get_current_font`, which ran the automatic check; the dialog appeared;
  after OK Claude answered and mentioned the empty `.notdef`; a second request showed no second dialog (the once-per-font memory holds across real requests).
- **Long wait:** with the dialog left open for 90 s the tool call stayed pending and Claude answered only after the click. So
  Claude Desktop's own tool-call limit is at least 90 s (its exact value is unknown); the server gives up at 120 s by design (the
  automatic check then reports `check_failed`; that path has not been seen live).
- **Blocking:** with the dialog open, `GET /health` timed out after 5 s: the listener serves nothing during a dialog (no re-entrancy, so no stacked dialogs).

**Not yet verified on real FontLab:** the explicit `check_notdef` tool and `get_glyph_outline(".notdef")` through Claude Desktop
(restart the listener first, which resets the once-per-font memory); a wait between 90 and 120 s and one beyond 120 s (the server
then gives up); a font with a drawn `.notdef` through Claude Desktop (no dialog expected; follows from the GET result); the `missing` dialog (stub-tested only; do not delete `.notdef` from a font that matters); whether other glyphs with
no outline (e.g. `space`) also have 0 layers (the outline route now answers `node_count` 0 for any zero-layer glyph); multi-layer
`.notdef`; `hasBody()`; whether a WRITE that timed out while a dialog was open is still executed after the click (the request waits in the
listener's socket queue; untested, which is why the timeout message says to check the state before repeating a change). One related observation from the v0.51 session:
after a Claude Desktop restart, a `create_glyph` call and then a read-only `list_glyphs` call each got no answer for 4 minutes (an unanswered Allow prompt was the likely cause); the font was
unchanged afterwards, i.e. the timed-out create had NOT been applied.

## 8. Glyph creation, names and Unicode (live-verified, test font; listener 0.50 / 0.51, server v0.13 to v0.16; server v0.17 and v0.18 are stub-tested only). Sections 8b to 8h below cover the geometry work of v0.52 to v0.82

**FontLab assigns the codepoint by itself from the name:** `B` 66, `C` 67, `D` 68, `eacute` 233, `uni00E9` 233, `uni0043` 67, `u1F600` 128512, and even LOWERCASE hex: `uni00e8` 232,
`uni00e7` 231. Made-up and suffixed names (`zzcontrol`, `B.alt`, `A.alt`, `m-n_o.p`, `9lives`, `.hidden`) get none. The codepoint is already readable inside the same create call.

**FontLab SKIPS the automatic codepoint when another glyph already holds it** (five observations): `B` created after `B.alt` was given 66; `C` after `uni0043` (67); `eacute` after `uni00E9` (233);
and, in the two early runs, `uni00E9` after `eacute` (233). The new glyph is created with no Unicode. **Lesson:** those two early runs were first read as "FontLab does not map uniXXXX names"
(wrong: `eacute` held 233). A negative live result must be checked for confounders, and a claim recorded only after a controlled run (here: `uni00E9` created on a font where nothing held 233).

**Duplicates by hand:** `set_glyph_unicode` accepts a codepoint another glyph holds, silently; both then report it. The v0.50+ reply names the other holders (`also_held_by`, `duplicate_warning`).

**Clearing:** setting a codepoint to 0 clears it (FontLab then reads back none). Until listener 0.51 the tool compared the re-read `None` with 0 and reported a failure although the codepoint HAD been cleared.

**FontLab keeps ONLY `A-Z a-z 0-9 . _ -` in a glyph name and silently strips everything else it is given, then creates THAT glyph:** non-ASCII letters, spaces, and `# / * : + @ ! $ % & ( ) ~ =` were all
stripped (a name ending in a non-ASCII e lost it; `a b` became `ab`; `a#b/c*d:e` became `abcde`; a lone non-ASCII letter became an EMPTY name, a glyph that no tool can address or delete because names must
not be empty). Accepted unchanged: `m-n_o.p`, a leading digit, a leading period, names of 64 and 130 characters (these stay hints in `name_warnings`: no leading digit, no leading period except `.notdef`,
at most 63 characters). Not probed: quotes, backslash, `[ ] { } < > , ; ? ^ |` and the backtick (refused by the safe-set rule anyway).

**What the tools do with this:** the server refuses any name with a character outside the safe set BEFORE calling FontLab, with a message that names the characters, says what FontLab would have created and
gives advice that fits (accented letter -> `eacute` / `uni00E9`; spaces -> `_` or `-`; punctuation -> leave out). The listener check `created_under_other_names` stays as a safety net (live: the error then says
that FontLab DID create a glyph, under which name). When a single-character or `uniXXXX` / `uXXXX` name comes back unencoded, the listener scans for holders (the server passes `scan_unicode`) and the
instruction tells the agent to ask the person, not to set it. For a plain multi-character name that comes back unencoded (it may be an Adobe Glyph List name FontLab skipped, e.g. `eacute`) the instruction
warns about the skip rule. Lowercase-hex names get a hint (convention says UPPERCASE; FontLab maps them anyway; other tools may not).

**Not tested / open:** secondary codepoints (`glyph.unicodes`; the scan reads only the primary `glyph.unicode`); standard Adobe Glyph List names that FontLab does not map at all (the server cannot tell them
from non-standard names); the stripped-character set beyond the list above; an older listener with a newer server (decided: no practical benefit; the `compatibility_note` and the `unknown` /
`unavailable` replies are stub-tested only); the `scan_error` / unreadable-glyph paths (stub-tested only).

## 8b. Glyphs made by `create_glyph` have no modern layer; creating it (live-verified, v0.70 to v0.72)

**The problem.** A glyph made by `createGlyph` has a legacy glyph but NO modern layer (`flGlyph.activeLayer` is `None`) until it is opened once in an editor tab, so nothing can be drawn into it and the modern margins cannot be read.
**The solution.** `flGlyph.findLayerCreate(name[, caseSensitivity])` creates the layer (live: it also appears on a REBUILT wrapper). The right layer name is `test_font` in the user's font; the listener derives it from the font's OTHER glyphs
(`_derive_layer_name`: up to 40 glyphs examined; every glyph that has a modern layer must report the same name; if none have one, or they disagree, nothing is created and the call is refused). `font.master` is an `fgLayer` whose `name` is an
EMPTY string, so it cannot supply the name. `getLayerByName(name, True)` and `addLayer(flLayer('name'))` were never needed.
**Who creates it.** `POST /glyph/width` and `POST /glyph/polygon` create the layer by themselves, and ONLY for a glyph that is positively empty (the replies say `layer_created`; creation counts as a change). The sidebearing routes never create a layer. If creation fails,
width falls back to the old legacy route (`legacy_empty_glyph`, reply carries `layer_create_note`). No editor tab is needed any more.

## 8c. Advance width and sidebearings (modern API, live-verified, v0.62 to v0.68)

- **Width** is the plain double property `flGlyph.advanceWidth` on the modern glyph. A glyph without a modern layer is written the legacy way ONLY when positively empty, otherwise refused. The legacy write path (`glyph.width = N` + `glyph.update()`) sometimes LOST work on glyphs with shapes: not used any more for glyphs that have shapes.
- **Sidebearings.** Every modern margin method takes a QTransform: `getLSB(tr)`, `getRSB(tr)`, `getSB(tr)`, `setLSB(v, move_guidelines, tr)`, `setRSB(v, tr)`, `setSB(l, r, move_guidelines, all_layers, tr)`; the earlier "Unexpected SeqBase<T> length" errors were wrong argument counts. The listener uses an
  IDENTITY transform: `PythonQt.QtGui.QTransform()` (fallback: the class in the `fontlab` module; the source is reported). `setSB(left, right, False, False, tr)` is the tool: it TRANSLATES the outline so LSB = left and RSB = right, and the advance width becomes LSB + ink + RSB. `setRSB` and `advanceWidth` change only the advance width.
  A drawn glyph starts with advance 0 (lsb = xmin, rsb = -xmax).
- **Verification:** `set_glyph_sidebearings` re-reads LSB, RSB and advance and checks advance = left + ink + right (ink read BEFORE the change). `get_glyph_sidebearings` reads lsb, rsb, advance, ink width (read-only). Refused (nothing called) when the glyph has no modern layer or no outline.
- **NEVER the legacy margin setters:** `glyph.leftMargin = N` CRASHED FontLab on a glyph whose shape was built through the modern API (v0.62); route=legacy for lsb/rsb is refused in the probe.
- Legacy margins are STALE right after a write; the width check uses the modern numbers.

## 8d. Drawing a polygon (live-verified, v0.70 to v0.75)

**Recipe:** `QtCore.QPointF` points -> `flContour(points)` -> `contour.closed = True` (read back; refuse unless true) -> `flShape()` -> `shape.shapeData.addContour(contour)` for each contour -> `layer.addShape(shape)` on the modern active layer, only if that layer is positively empty.
Everything is built DETACHED and checked first; `addShape` is last, so a failure before it changes nothing. Several contours go into ONE shape. Dead forms (live): `shape.addContour(...)` on a detached `flShape` fails with "Unexpected SeqBase<T> length"; `flShape(flShapeData)` and `flShape(contour)` are refused; the `route=pen` route (`glyph.getPen()`) wrote into a stray "Body" layer the editor does not draw.
**v0.81 / v0.82 additions:** coordinates are now ROUNDED to whole units with rule B (`floor(v + 0.5)`: a half rounds UP, 2.5 -> 3, -2.5 -> -2) BEFORE drawing and every changed coordinate is listed in `coordinates_rounded` (before, FontLab rounded silently through `flContour(points)` and only counts were verified); a contour that collapses to fewer than 3 distinct positions after rounding is refused (HTTP 400). Both drawing tools need listener 0.82 (layer guard, section 8h).
**Limits:** `draw_polygon(name, points=None, contours=None)`, exactly one of the two; 3 to 500 points per contour, 1 to 20 contours, at most 2000 points in total; numbers within +-20000; at least 3 distinct positions per contour; straight segments only; the glyph must hold NOTHING yet (a layer that already has shapes is refused).
**Verification:** 1 shape, node total = points, contour count (`contours_ok`, through `getContours()`; null when unreadable). Success is reported only after the re-read agrees. Drawing does NOT change the advance width (`set_glyph_width` or `set_glyph_sidebearings` afterwards).
**Server side:** `write_glyph_polygon` needs listener 0.82 since server v0.24 (layer guard; it needed 0.75 for `contours` and 0.72 for one contour before); `_check_polygon_points` validates before anything is sent.

## 8e. Reading an outline back from the modern layer; direction; curves (what is known)

**Why:** the legacy reader (`/glyph/outline`) lags and is BLIND to shapes drawn through the API; `modern_check` compares the modern node count with the legacy count, and `modern_outline` (v0.74) is added whenever the modern layer has nodes and the two disagree. The server then answers with `source: "modern layer"`.
**Proven live calls:** `layer.getContours()` returns a plain Python list (indexed only when it is a real list/tuple); `contour.getNodeAt(i)` after a range check against `nodesCount`; node reads `x, y, isOn(), isOff(), isCurve(), smooth, index`; contour reads `closed, clockwise, nodesCount`. `layer.shapes` is a list. `layer.getShapes()` raises IndexError. `contour.nodes` is a METHOD (calling it is untested). Limit `_MODERN_OUTLINE_MAX_NODES = 5000`; no partial outlines (any failed read gives `{available: false, error}`).
**Result fields (server):** contours (`closed`, `clockwise_reported`, `direction_computed`, `flag_follows_known_inversion`, `node_list` with x/y/kind/curve/smooth, `curve_type`, `svg_path` for straight and cubic closed contours; v0.24), `ink_bbox`, `ink_bbox_exact`, margins, `verification`. Status is `verified` only for straight-segment outlines whose node box equals the modern lsb and ink width; since server v0.24 cubic outlines are `verified` too (section 8g); quadratic or malformed curves stay `unverified` with a reason.
**DIRECTION (live, three glyphs):** FontLab's `contour.clockwise` flag is the OPPOSITE of the y-up geometry: a counterclockwise contour reports `clockwise: true`, a clockwise one `false` (confirmed with a house, a square, and both ring contours). The outer contour of the real glyph `A` (cubic test font, Power Brush shape) is COUNTERCLOCKWISE in y-up. So: outer contours counterclockwise, counters (holes) clockwise. One real sample: a strong hint, not a law. The server warns only when a flag does NOT show the known inversion.
**Curve building blocks (from `/debug/classdir`; the working recipe is in section 8g):**
- `flNode` constructors: `flNode()`, `flNode(Node)` (clone), `flNode(QPointF position[, string nodeType="on"[, int nodeKind=None]])`, `flNode(double x, double y[, string nodeType="on"[, int nodeKind=None]])`. `flNode.NodeType` is a real Python dict (`On` 1, `Off` 2, `Curve` 4, `AnyNodeMask` 7); `flNode.NodeKind` and `flContour.FigureType` are dicts too (their contents were printed by a `names` probe; re-run it). Members worth a names-only look: `convertToCurve`, `convertToCurves`, `convertToLine`, `smooth`, `nextNode`, `prevNode`, `type`, `isCurve`.
- `flContour` constructors (docstring): `flContour()`, `flContour(list(Node)[, bool closed=false])`, `flContour(list(QPointF)[, NodeType=On[, bool closed=false]])`, `flContour(QRectF)`, `flContour(QLineF)`. **Live:** only forms with at most 2 arguments exist; `flContour(points, On, True)` is refused ("Incorrect # of args"); `flContour([flNode, ...], True)` is refused ("QPointF expected"); NONE of the constructor forms closes the contour (set `contour.closed = True` afterwards); `flContour(QRectF)` gives a closed 4-node contour. Members of interest: `insert`, `insertNodeTo`, `insertSafeNodeTo`, `add`, `nodes` (method), `takeNodes`, `clearNodes`, `getNodeAt`, `setPoint`, `convertTTtoCurve`, `segments`, `segment`, `getSegment`, `closed`, `closedT1`.
- Reading already shows `Off` / `curve` nodes; cubic = exactly two handles between on-curve nodes (section 4).

## 8g. Cubic curves: `draw_path` (live-verified, listener 0.76 to 0.82, server v0.23 / v0.24)

**Facts found live (FontLab 8.4.2.8950, disposable font; every item was a controlled one-variable probe):**
- `contour.getNodeAt(i)` works on DETACHED contours. Node reads: on-curve `isOn` true / `isCurve` false; a cubic control point ("handle") `isOn` false, `isOff` false, `isCurve` true, `type` "curve" (strings `"on"` / `"curve"`); zeros print as `-0.0`.
- **`node.convertToCurve(False)`** returns True and converts the segment that ENDS at the called node: two handles are inserted directly BEFORE it, by default at about 33% / 67% of the edge (132 / 268 on a 400 edge). On **node 0** it converts the CLOSING segment (last node back to node 0) and APPENDS the two handles at the END of the node list (indices n, n+1; first the one next to the last node, e.g. (0, 268) then (0, 132) for a square). `convertToCurve(True)` marks BOTH ends smooth and auto-places handles (not used).
- **`node.smooth = True`** sticks and IMMEDIATELY realigns the neighbouring handles collinear through the node (lengths kept, rounded to whole numbers). **Moving a handle afterwards by `x` / `y` assignment does NOT move its partner** (even on a smooth node): there is no automatic pairing, so collinearity at smooth nodes is checked by OUR code.
- **Precision by API route** (probe curve4): `contour.setPoint(i, QPointF)` ROUNDS to the nearest integer; `flContour(list of QPointF)` ROUNDS (0.5 -> 1.0); `moveBy(dx, dy)`, `node.x` / `node.y` assignment and `node.position = QPointF` KEEP fractions. The tools still round on purpose (rule B) because whole units are what the font stores here.
- `flContour.insert(index, flNode)` failed ("QPointF expected"): abandoned, not needed. `shape.shapeData.addContour(contour)` + `layer.addShape(shape)` works for contours with curve nodes (as for polygons).
- FontLab's own extents agree with the exact cubic maths: a bulging edge with handles at x = 500 gives ink width 475 (= 400 + 0.75 x 100); handles at x = -100 give left sidebearing -75; the rounded test outline gave left -2 / right -10.75 / ink 12.75 (analytic 10.75). FontLab's `clockwise` flag stays inverted (section 8e) for curve contours too.

**`draw_path(name, contours)`** (listener `POST /glyph/path`, server v0.23). `contours`: 1 to 20 lists of 3 to 500 point objects, at most 2000 NODES in total (control points count); numbers within +-20000. A point is `{"x", "y"}` plus optional `"c1"`, `"c2"` (BOTH or neither; `{"x","y"}` each) = the two control points of the cubic segment that ENDS at this point, `c1` next to the previous point, `c2` next to this point; for the FIRST point they describe the closing segment (last point back to the first); optional `"smooth": true`.
**Build order (detached):** `flContour` from the on-curve points -> `closed = True` -> `convertToCurve(False)` on the curved points in DESCENDING index order (node 0 last) -> `smooth = True` on the flagged nodes BEFORE the handles (setting it realigns handles) -> handles placed LAST by `x` / `y` assignment -> the detached contour is read back and must match the request node by node (position, on-curve vs handle, smooth flag) -> smooth gate -> `shapeData.addContour` + `layer.addShape` LAST -> the modern layer is read back (`_read_modern_outline`) and compared node by node (`nodes_match`); success needs shapes 1, the node total and `nodes_match`.
**Smooth gate:** at every smooth node the previous and the next node (a handle, or the neighbouring on-curve point for a straight segment) must lie on opposite sides of one straight line through it, within 2 degrees (`_PATH_SMOOTH_TOLERANCE_DEG`); a neighbour on top of the node cannot define a direction. Otherwise nothing is built (the reply says which node; no layer is created).
**Rule B:** every coordinate (points and control points) is rounded to the nearest whole unit, half up; the reply lists each changed coordinate in `coordinates_rounded` (`contour`, `point`, `field` like `x` or `c1.y`, `requested`, `used`) plus a `rounding_note`. A request that collapses below 3 distinct on-curve positions is refused.
**Limits / not covered:** closed contours only; into an EMPTY glyph only (section 8h); one shape; cubic fonts only (the test font is cubic; quadratic output untested); the advance width is not changed by drawing. Reply fields: `drawn`, `verified`, `nodes_match`, `coordinates_rounded`, `points`, `curved_segments`, `contours`, `contour_sizes` (nodes per contour), `shapes`, `nodes`, `left`, `right`, `advance_width`, `ink_width`, `layer_created`, `display_note`, `font_modified`.
**Reader (server v0.24, modern route):** cubic control points are labelled `kind: "Curve"` (before: "Off" with `curve: true`, which looked quadratic); `kind: "Off"` is a quadratic off-curve point; each contour reports `curve_type` (none / cubic / quadratic / mixed); closed cubic contours get an `svg_path` with `M / L / C`; the exact extents (derivative roots of every cubic segment) make `ink_bbox_exact` true and the verification `verified` when the box equals FontLab's modern left sidebearing and ink width (tolerance `_CURVE_BOX_TOLERANCE` 0.05); quadratic points, a run of control points that is not exactly two, and open contours stay `unverified` with a reason.
**Live record (test font, glyphs made with `create_glyph`, FontLab quit without saving):** v0.78 / v0.79 first curve (rounded corner; the GUI showed the handles 355/0 and 400/45); v0.81 / v0.82: bulging rectangle (ink 475), circle of 4 smooth nodes (400), curve across the closing segment (left -75, handles at the END of the list), curved counter (2 contours, 10 nodes), rule B (0.5 -> 1, 10.49 -> 10, 10.5 -> 11, 3.2 -> 3, 7.5 -> 8, -2.5 -> -2; margins agree with the analytic extents), smooth gate refusal (non-collinear neighbours: refused, nothing changed). v0.82: all four outlines read back `verified` through `get_glyph_outline` with `Curve` labels and exact extents.

## 8h. Layer guard (defect found live in v0.81, fixed in listener 0.82)

**Defect.** A SECOND `draw_path` into a glyph that already held a drawn outline did not refuse: the outline was REPLACED (probe `/debug/trylayer?stage=state`: the glyph still had exactly ONE layer, `test_font`, holding only the new shape). Cause (from the code and the probe; the exact FontLab behaviour of `findLayerCreate` on an existing layer was not isolated): right after the first draw the cached modern glyph can report NO active layer while the legacy view still lags and reads the glyph as empty, so the listener took it for a glyph that never had a layer and called `findLayerCreate` again, which hands back an EMPTY layer. `draw_polygon` and `POST /glyph/width` used the same code path (since v0.72).
**Fix (0.82).** Before `findLayerCreate` is ever called, `_ensure_modern_layer` asks WITHOUT creating anything: `getLayerByName(name, False)` and `findLayer(name)` (both proven read-only live: the probe returned the existing layer). If a layer of that name exists, or the question cannot be answered (method missing or raising), nothing is created and the call is refused ("the glyph already has a layer named ..." / "the glyph may already have a layer (...)"); `POST /glyph/width` then does NOT fall back to the legacy write (which can lose work). A glyph with no layer at all still gets one created as before (live: `layer_created: "test_font"`). Server v0.24: `draw_path` and `draw_polygon` need listener 0.82 and say so before sending.
**Live status:** after the fix, a second `draw_path` and a second `draw_polygon` on drawn glyphs were refused with "layer not KNOWN to be empty" and the outlines stayed unchanged (checked through `get_glyph_outline`). The guard's OWN refusal path (wrapper without an active layer although the layer exists) was NOT seen live in that run; it is covered by a stub test that fails on v0.81 and passes on v0.82. Side effect: a genuinely empty glyph whose layer is merely inactive is also refused (safe, rare; can be loosened later).

## 8l. Unsynced layers and the update guard (live-proven in v0.84 to v0.86 sessions; guard in listener 0.87, server 0.27)

**v10 update (read 8m first):** the guard below is still in force, but since listener 0.89 the write tools sync a glyph themselves right after the write (`fontlab.Update(<flGlyph>)`), so the unsynced state normally lasts for milliseconds and the guard only acts after a FAILED sync. The statement below that "nothing syncs except editor-open + next request" is obsolete. The guard was verified live in v10 (139a / 139b: the unsynced drawing survived a create and `display_refresh: skipped` appeared; 142: no skip needed).

**Background (extends section 8i).** A layer made or changed through the modern API (`draw_polygon`, `draw_path`, width or sidebearing writes, automatic layer creation) exists only on the MODERN side. The legacy view of that glyph stays empty (legacy `layers` 0, `/glyph/outline` says `agree: false`, the grid tile stays blank) until FontLab "syncs" it.
**The data loss (live, one-variable runs, tests 126 to 134 of this session):**
- The legacy `font.update()` throws away EVERY unsynced layer in the font (129: two layers lost at once; the first-only / only-layer theory was refuted). It is called by `create_glyph`, `set_glyph_unicode` (together with `glyph.update()`), `delete_glyph` and the legacy width route. A drawing "disappears" with the next create.
- **133 (controlled):** `font.createGlyph(name)` ALONE keeps the layers; `createGlyph` + `font.update()` loses them. **134:** `set_glyph_unicode` (glyph.update + font.update) also wipes them.
- **Sync trigger (130 / 131):** opening a glyph in an editor tab (a GUI event) followed by the NEXT API request makes FontLab sync ALL glyphs (the grid tiles repainted when the next request ran, not at the GUI step). Layers synced this way survive creates even with the editor tab closed; layers drawn AFTER that sync are unsynced again.
- **Useless candidates (132, probe `/debug/trysync`):** `flPackage.update()` and `flWorkspace.instance().update()` both ran (return True) and changed nothing: outline still `agree: false`, tiles blank, `isChanged` false before and after; the next create still removed the layers.
- A pre-created glyph list does not protect either (pre-creating all glyphs first did not help).
**The guard (listener 0.87, section 12 for the tests).** Registry `_UNSYNCED` (per font key = `str(font.path)`, cap `_UNSYNCED_MAX` 500, an overflow flag). Registered by: `_modern_edit_target` when it creates a layer (`layer_created`), `draw_polygon` and `draw_path` when something changed, `set_glyph_width` (modern route, on success), `set_glyph_sidebearings` (on `changed`). The reply of those tools carries `synced_with_fontlab: false` and a `durability_note`.
**Before each legacy update call** (`create_glyph`, `delete_glyph`, `set_glyph_unicode` = `glyph.update()` + `font.update()`, `_set_width_legacy`) `_guard_decide(font)` classifies every remembered glyph (`_guard_classify`, read-only, never raises): `gone` (no such glyph any more) and `synced` are forgotten; `lost` (the modern wrapper reports no layer) is forgotten and REPORTED in `layers_missing_since_drawn`; `at_risk` = legacy `layers` 0, or legacy node count differs from the modern node count, or legacy `width` differs from modern `advanceWidth` by more than 0.01; `unknown` = any read fails (wrapper, layer, counts). `synced` needs legacy layers > 0, equal node counts and (when both readable) equal widths. If any glyph is `at_risk` or `unknown`, or the overflow flag is set, or the check itself fails, **the update calls are skipped** and the reply gets `display_refresh: "skipped"`, `display_refresh_skipped_to_protect` (names), `display_refresh_unreadable_glyphs`, `display_refresh_note`. The operation itself still runs (the new glyph is created, the codepoint set, the glyph deleted: all verified by the usual re-read). With nothing at risk the behaviour is exactly as in v0.86. The guard block never calls any update / save / export function (a static scan checks it). Delete: the check runs after `removeGlyph`, so a deleted unsynced glyph is `gone`.
**Known limits:** only glyphs changed through THIS listener run are remembered (a drawing made before a listener restart is unprotected); a glyph is forgotten only when a later guard check finds it synced, so a skipped refresh can last until the person opens a glyph in an editor and any request follows; `font.update()` was the only call proven harmful, the guard also skips `glyph.update()` in the two places that pair it with `font.update()`.
**Not yet proven live:** that the guard really keeps a drawing through a create in FontLab (the stub font WIPES unsynced layers in `update()` like FontLab does, so the stubs show it; the live run is test 136a / 136b, Appendix A); whether `set_glyph_unicode` on the unsynced drawn glyph ITSELF would lose it (the guard skips the update anyway); whether `font.update()` reverts a width or sidebearing edit on an already SYNCED glyph (the guard's width comparison treats a mismatch as at risk, untested live); whether File > Save / Save As keeps an unsynced drawing (test 135, DEFERRED by the user); whether the grid lists a plain-created glyph before a refresh (display refresh skipped).

## 8m. Automatic sync after modern writes (live-proven in the v10 session; listener 0.89, server 0.29)

**The question and the finding.** Sections 8i and 8l describe the root problem: a glyph written through the modern API (`flGlyph`) stays UNSYNCED, i.e. FontLab's legacy view (`fgGlyph`) does not follow, until FontLab "syncs" it. v9 knew one trigger only (open the glyph in an editor, then the next API request). **v10 found the direct call: `fontlab.Update(<flGlyph>)`.** The module function `Update` is documented by FontLab as "Update object and it's visual representations. Without argument update all changed objects. Update([fgGlyph|fgFont|flObject object])" (probe 138). Glyphbridge calls it with ONE argument, the modern glyph wrapper (the cached `flGlyph` of `_modern_wrapper`). **Never call it without an argument** (that updates ALL changed objects) and never `UpdateAll()`.

## 8n. Listener-side stale-view fallback (listener 0.88, server 0.28; live-proven in 139b)

**What it does.** `GET /glyph/outline`: when the legacy node count equals the modern count (so the old `modern_check` said `agree: true`) and the legacy margins were read, `_reader_margins_compare(w, legacy_margins)` compares modern left / right / advance with the legacy `left` / `right` / `width` (tolerance `_READER_MARGIN_TOLERANCE = 0.05`). `modern_check` gains `margins_agree`: `true`, `false` (plus `margins_differ`, `legacy_margins`, `modern_margins`) or `null` (plus `margins_note`: no QTransform, unreadable, a legacy value not a number). **5. The product: listener `GET /kerning/pairs` (0.94) and `POST /kerning/pairs` (0.95), function `get_kerning_pairs(pairs, text)`.**
- **Verified read, so NO `go` gate and NO per-run counter** (a read-only call that was proven harmless in 150 to 154b). The ONLY member of the kerning object it ever touches is `get`, once per pair (spy test: every other member, among them `set remove clear addGroup deleteGroup renameGroup scale setPlainPairs asDict getPlainPairs getPlainPairsDict items keys values has_key hasGroupKerning groups`, aborts the test; a static scan of the function source checks the same).
- **Input: exactly one of** `pairs` or `text`. `pairs`: GET `?pairs=A:V,T:o` (a string; `:` and `,` cannot occur in glyph names), POST body `{"pairs": [["A","V"],["T","o"]]}`; 1 or more pairs; each name 1 to 63 characters from `A-Za-z0-9._-`, whitespace around a name is stripped. `text`: GET `?text=...` (percent-encoded UTF-8; a `+` is a space), POST body `{"text": "..."}`; 2 or more characters, no control characters (code points below 32 and 127 to 159 are refused; U+00A0 is allowed). **No upper limit in v0.95** (v0.94 allowed 40 pairs / 41 characters; the cap was removed by the user's decision). Bad input answers HTTP 400 with `{"error": ...}`; an unexpected exception answers 500; a POST body must be a JSON object with only the keys `pairs` and `text` (anything else, a non-list `pairs`, a non-string `text`: 400), invalid JSON or invalid UTF-8: 400 "request body was not valid JSON".
- **No font:** `CountFonts() == 0` (checked FIRST; this route uses the correct "open" test of section 8k) or `CurrentFont() is None` answers `{"open": false}` and `CurrentFont()` is not even asked when `CountFonts()` is 0.
- **Glyph names must exist** (the glyph set is read from `font.glyphs`); an unknown name gives that pair an `error` ("no glyph named 'Q'") and the other pairs are still read.
- **Text mode:** every character is mapped to the ONE glyph whose PRIMARY Unicode (`glyph.unicode`, plain int) is that code point; a character with no glyph, or with several glyphs (the reply lists up to 5), gives each pair it belongs to an `error`; glyphs whose Unicode could not be read are counted and named in the error ("no proof that none has it"). The neighbours of the text are the pairs (a text of n characters has n - 1 pairs, `chars` shows the two characters). Secondary Unicodes are not looked at.
- **Per pair:** `getter((left, right))` once; `None` -> `value 0`, `kerned false`; a finite number -> `value`, `kerned` = (`value != 0`); an exception, a bool, a string, NaN or infinity -> an `error` for that pair, **never a zero**.
- **Reply:** `open`, `mode` (`pairs` | `text`), `units_per_em` (from `font.info.unitsPerEm`, `null` unless a plain number), `count`, `errors`, `table_size` (= `len(font.kerning)` before the batch), `side_effect_detected` (table size before != after; `null` when a size could not be read), `results` (`left`, `right`, `chars` in text mode, `value`, `kerned` or `error`). Values come as floats (`-152.0`).
- **Transport facts (not limits chosen by us):** the listener's request head is read up to 65,536 bytes (a GET address is therefore limited to about that); a request BODY is read up to 1,000,000 bytes (roughly 30,000 pairs) and a larger one arrives cut off and answers 400 "not valid JSON"; every call runs on FontLab's main thread (QTimer-polled socket), so a very large read keeps FontLab busy while it runs. Real timings are NOT measured yet (K14).

**6. The product: server tool `get_kerning` (v0.30, v0.31), function `read_kerning(pairs, text, confirmed_large_read)`.**
- Signature `get_kerning(pairs: list[list[str]] | None = None, text: str | None = None, confirmed_large_read: bool | None = None)`. Exactly one of `pairs` / `text`. Validation happens BEFORE anything is sent (not even the version check): `pairs` a non-empty list or tuple of 2-element lists or tuples of strings matching `^[A-Za-z0-9._-]{1,63}$` after stripping; `text` a string of 2 or more characters without control characters; `confirmed_large_read` `None` or a real bool.
- **Approval threshold (v0.31, `_KERN_CONFIRM_ABOVE = 250`):** a request for MORE than 250 pairs (for text: more than 251 characters) with `confirmed_large_read` not exactly `True` is refused before sending, with the message "This request would read N kerning pairs, more than the 250-pair threshold, and nothing was read. Do NOT repeat the call yet. A large read costs many tokens: tell the person how many pairs you want to read and why, and ask whether they approve. Only after they have said yes, call get_kerning again with the same arguments and confirmed_large_read=true. Never set that flag without the person's approval." Name validation comes first, then the threshold. Exactly 250 pairs needs no approval; the flag on a small request is accepted and ignored. The flag is the agent's own claim: **a tool cannot verify that a human said yes** (decided and told to the user in the proposal).
- Then `_require_listener((0, 95), "get_kerning")` (an older listener is refused BEFORE sending; an unreadable version lets the call decide), then `POST /kerning/pairs` with `{"pairs": [[l, r], ...]}` or `{"text": "..."}` (the server always uses POST; the GET form of the listener is for browsers and PowerShell). Timeout `max(TIMEOUT_SECONDS, 5.0 + pairs / 100)` seconds (5.0 for a small read, 7.5 s for 250 pairs, 305 s for 30,000).
- Reply handling: `open` false -> the `NO_FONT` text; a listener `error` -> `ToolError("Kerning could not be read: ...")` (cut at 600 characters); `results` must be a list of exactly the expected length, otherwise "the listener's answer did not match the request"; every entry is rebuilt and type-checked: the echoed pair must equal the pair asked (else an error entry), an `error` text is kept (cut at 600), a `value` must be a finite non-bool number (else an error entry: "carried no usable number, so it was not read"), `kerned` is RECOMPUTED from the value (the listener's flag is not trusted), whole numbers become ints (`-152.0` -> `-152`, `-0.0` -> `0`), unknown fields are dropped. The server counts `errors` itself. `table_size` and `units_per_em` are forwarded only as plain numbers.
- Reply: `mode`, `units_per_em`, `table_size`, `count`, `errors`, `results`, `agent_instruction`, plus `side_effect_detected: true` (with a WARNING sentence in the instruction) only when the listener saw the table size change, and `large_read_confirmed: true` only after an approved large read. `agent_instruction` says: values are in font units (`units_per_em`), NEGATIVE = closer together, positive = apart; FontLab's own numbers including class kerning; `kerned: false` with 0 = FontLab has no kerning for that pair; a result with an `error` was NOT read and must never be treated as zero; feature-based (GPOS lookup), contextual and multi-master kerning are NOT covered; only the requested pairs were read, do not ask for the whole table; `table_size` 0 = the font has no kerning at all.
- **Pure read:** no `_note_change`, no `finish_changes`, no save (a static scan test checks the function source: no POST helper other than the read, no change tracking, no save).
- Tool docstring (tested for these phrases): "exactly one of", "Never ask for the whole kerning table: read only what the task needs", "There is no upper limit, but more than 250 pairs ... is refused until the PERSON has approved it", "Never set confirmed_large_read=true on your own", "Needs listener v0.95", "never a zero".

## 8i. Stale legacy view after API writes (live finding on v0.24; detection in server v0.25, wording v0.26)

**What happens.** FontLab keeps two views of a glyph: the MODERN layer (`flGlyph.activeLayer`, what every write tool changes and what `get_glyph_sidebearings` reads) and the LEGACY view (`fgGlyph`, what the old reader `GET /glyph/outline` walks). A glyph that was never opened in an editor has an empty legacy view (`legacy reader sees 0 nodes`), so the server takes the modern route (`source: "modern layer"`, current). A glyph that HAS been opened in an editor tab has a populated legacy view, the server takes the legacy route (no `source` key, no `modern_check`) and that view does NOT follow later modern writes: after `set_glyph_sidebearings(40, 60)` (and again after `(20, 30)`) the legacy nodes still showed the old x range, the legacy margins the old values (0 / 100, 0 / 50), and only the advance width was new. The v0.24 reader compared the legacy nodes with the legacy margins (equally stale) and said `verified`. FontLab's own X/Y readouts and the modern reads had the new geometry.

**What was proven live (one variable at a time, glyph `stl85a`, opened in an editor tab):**
- Baseline before any change: `verified`, `modern_margins_check: agrees`.
- Immediately after `set_glyph_sidebearings(20, 30)`: `unverified`, `stale_legacy_view: true`, legacy margins 0 / 50 against modern 20 / 30, advance 525 on both (the reply names both).
- A plain click on the grid tab and back: legacy view STILL stale. About 7 minutes of waiting with no GUI action: STILL stale (read twice).
- Closing the glyph's editor tab (X) and double-clicking the thumbnail: legacy view refreshed (`verified`, nodes 20 to 520, handles at 520, margins 20 / 30, `modern_margins_check: agrees`).
- NOT tested: whether selecting a node in the editor also refreshes it. In the earlier `grd83a` run the stale view cleared after the user switched to the grid tab and back AND inspected nodes (screenshots with X/Y readouts); that run did not separate the factors, so only "close and reopen the tab" is recorded as confirmed.
- On the legacy route `bounding_box_check.raw_node_box` is the box of ALL nodes including control points (0 to 500 for the bulging rectangle) while the ink extents and margins use the exact curve (0 to 475); the two agree through FontLab's own `fontlab_box`, and the result is `verified`.

**What the server does now (v0.25 / v0.26):** `_stale_legacy_check` (legacy route only; skipped when the status is already `unverified`, when `modern_check.modern_layer` is not true, or when the modern layer was used) calls `GET /glyph/sidebearings?name=...` once and compares `lsb` / `rsb` / `advance` with the legacy `margins.left` / `right` / `width`, tolerance `_STALE_MARGIN_TOLERANCE = 0.05`. It never raises. It does not change the listener. Tests: part 15 of `create_unicode_tests.py` (15a live case, 15b detail, 15c agree, 15d 0.04 tolerated, 15e 0.06 flagged, 15f advance only, 15g read fails, 15h modern not readable, 15i not a number, 15j legacy margins missing, 15k no modern layer, 15l old listener, 15m modern switched off, 15n old node-count path, 15o already unverified, 15p calibrated checked too, 15q docstring, 15s v0.26 wording, 15r no write and no save); a mutation test (check disabled) turns 15a back into `verified`.

**Advice for agents and for the person:** after changing a glyph through the API, trust `get_glyph_sidebearings` and the modern reads; if `get_glyph_outline` says `stale_legacy_view`, ask the person to CLOSE the glyph's editor tab and reopen it from the grid, then read again. A glyph never opened in an editor is always read from the modern layer and is not affected.

**Possible later improvement: BUILT in v10** (listener 0.88 / server 0.28, section 8n): the listener returns the modern outline whenever the modern margins disagree with the legacy ones, and since listener 0.89 the write itself syncs the glyph (8m), so the refresh recipe above (close the editor tab) is no longer needed in normal use.

## 10. Hard rules

- **No `[]`, `.get()`, `.keys()` on any native FontLab/fontgate object** (native crash that `try/except` cannot catch). Indexing only
  on real Python lists/tuples (`layer.shapes`). `len()` and zero-argument calls have been reliable.
- Probe unknown objects in stages: names only (`dir`) -> read named attributes -> call whitelisted getters. Never call setters,
  `transform`/`scale`/`translate`, `remove`, `release`, `clone`, `apply*`. One question per probe. `/debug/walk` enforces this.
- **Warm-up:** touch `glyph.layer`, then read `bodyLayer` (otherwise `None` intermittently).
- Reversible value writes are not gated; destructive operations are; anything that changes UI state or constructs objects needs `go=yes`.
- When introspection contradicts itself (attribute sometimes `None`, sometimes populated), suspect FontLab's API before the code.
- Live tests that create glyphs go on the disposable test font; creating a glyph with a name FontLab alters leaves a glyph that may be nameless and undeletable by our tools: only the refusal in the server prevents it.
- **Never subscript a native FontLab object** (`layer[N]` crashed it); iterate or index only REAL Python lists/tuples (`layer.getContours()`, `layer.shapes`), and range-check `getNodeAt(i)` against `nodesCount`.
- **Never use the legacy margin setters** (section 9). Margin and width WRITES go through the modern `flGlyph` only, after the layer exists.
- **A drawing or write is reported successful only after a re-read agrees**; detached objects are built and checked first, the attaching call is last. For curves the re-read is node by node (`nodes_match`), not counts.
- **Never call `findLayerCreate` (or any create) before asking read-only whether the layer already exists** (section 8h). The legacy view LAGS after API writes: "legacy says empty" proves nothing about a glyph drawn through the API.
- Curve building order is part of the recipe: curve conversion descending, smooth flags before handles, handles last (section 8g).

- **Never call the legacy `font.update()` / `glyph.update()` while a glyph that was drawn or changed through the modern API may be unsynced (v9, section 8l).** New code that needs a display refresh goes through `_guard_decide(font)`; a tool that registers modern changes calls `_guard_mark` / `_guard_register`. Never use `flPackage.update()` / `flWorkspace.update()` as a cure (useless).
- **"A font is open" means `CountFonts() >= 1`, not `CurrentFont() is not None`** (placeholder `fgFont`, section 8k). `flPackage()` creates a font immediately: only in gated probes, once per listener run, never as a side effect.
- **Check file identity before editing (v8):** `md5sum` the working copies against the last delivered identity at the start of any turn that patches files; if they differ without an explanation, say so, diff against the untouched uploads, review, test and mutation-test before adopting (section 12, provenance incident).
- **Do not read whole outlines of big glyphs:** the reply costs about 65 tokens per node. Above about 150 nodes use the draw reply (`nodes_match`, margins) and `get_glyph_sidebearings`, or ask for a summary mode (section 14 P2).
- **Never trust `verified` on the legacy route without `modern_margins_check`:** it is the only protection against a stale legacy view (section 8i).
- **Sync rule (v10):** after a modern write a glyph is synced with `fontlab.Update(<modern glyph wrapper>)` ONLY (`_auto_sync` through `_guard_mark`); one glyph, one call, never without an argument, never `UpdateAll()`, never the assign family (`assignFgLayer`, `assignFontGateData`) or `replaceGlyph` (legacy-to-modern direction, suspected cause of the data loss). A new tool that writes through the modern API must call `_guard_mark` (it then syncs and reports `fontlab_sync` by itself). A glyph counts as synced only after `_guard_classify` says so, never because the call returned.
- **Reading rule (v10):** trust `modern_check.margins_agree`: when it is false the listener already supplies `modern_outline` and the server answers from the modern layer; never answer from a legacy view that disagrees with the modern layer.

- **Kerning rules (v11):** (1) **Never read the whole kerning table or the whole font to answer a kerning question**: ask for the few pairs the task needs (`get_kerning`). (2) The ONLY call on `font.kerning` is `get((left, right))`, once per pair; no `asDict`, `getPlainPairs`, `items`, `keys`, `values`, no `set`, `remove`, `clear`, `addGroup`, `deleteGroup`, `renameGroup`, `setPlainPairs`, `scale` (a spy fake in the tests aborts on each of them). The "no `.get()` on native objects" rule of this section has this one documented, gated-then-verified exception. (3) A pair that could not be read is an **error, never a zero**; only `None` from FontLab means "no entry" (value 0, `kerned false`). (4) More than 250 pairs in one call needs the person's approval; an agent NEVER sets `confirmed_large_read=true` on its own. (5) Group kerning is resolved by FontLab (`get`), never by our code; group names are not accepted as input. (6) Kerning values are in font units; always report `units_per_em` with them; feature-based, contextual and multi-master kerning are not covered and the agent must say so when it matters.

## 11. Known limits and untried ideas

- **Components** are not followed (the direct route declines a component shape, falls back and says so). `GlyphComponent`, `glyph.components`, `flLayer.components(Count)` untried beyond `len(glyph.components)`. This is the biggest READING gap for real fonts (accented letters are usually composites): section 14 P1.
- **Open contours** are assumed closed when READ (never tested; a cubic reader path returns `unverified` for an open contour); the DRAWING tools only make closed contours (section 14 P2). **Several elements** in one glyph: contours are assigned to elements in FontLab's listed order, confirmed only by simulation plus the combined bbox/margin agreement.
- **Power Brush:** only the generated outline is read (shape flagged composite); skeleton/stroke settings are not exposed.
- **Rotation and mirroring** on real data: simulated only. **Multi-layer / multi-master:** untested (only the layer `test_font` of the user's font has been seen).
- **Large glyphs:** evidence in hand (v8): 180 nodes drawn and read back completely, 990 nodes drawn (`nodes_match`, margins agree), `get_glyph_sidebearings` fine on it. NOT tested: a request near the 2000-node cap, the outline route on 1000+ nodes against the 5 s timeout, real timings in seconds (the tools show none), `_MODERN_OUTLINE_MAX_NODES = 5000`. Decision of the user (v8): all tests with glyphs of more than about 150 nodes are postponed to the VERY END (section 14, block LAST).
- **Straight-line-only and multi-contour glyphs** are read and written live: square with a hole (`ringtest`), an O with a counter (GUI-confirmed, section 8j), a diagonal circle, an S-like blob. A real designed letter READ from a real font (many curves, hints) is still unchecked (read-only reads of a few glyphs of the Arial font opened from the system are a cheap next step, section 14 P1).
- **Saving is deliberately NOT offered** (save policy, section 2: nothing calls `font.save()`, a test guards it; the person saves). Geometry is written only through the drawing, width and sidebearing tools of sections 8b to 8d and 8g (`shapeData.addContour` + `layer.addShape`, `setSB`, `advanceWidth`); `createContour/deleteContour` untried; there is NO tool that edits or removes an existing outline.
- **No tool lists every glyph's codepoint:** an agent learns who holds a codepoint only from `create_glyph` / `set_glyph_unicode` replies.
- TypeRig was deliberately not adopted. FontLab docs: https://fontlabcom.github.io/fontlab-python-docs/ (`fgFont`, `fgLayer`, `fgGlyph`).
- **Limits of the drawing tools (v0.82 / v0.26):** `draw_polygon` straight segments only; `draw_path` straight and CUBIC segments; both closed contours only, ONE shape only (several contours in one shape work; several separate shapes do not), only into an EMPTY glyph, whole units only (rule B). `verified` covers straight and cubic outlines; quadratic is `unverified`. Cubic output was tested only in the cubic test font. `set_glyph_sidebearings` / `set_glyph_width` on a curved glyph are now tested live (v8). **Nothing has been tested after a save and reopen of the font** (release-candidate item).
- **Reader limits (v8):** `get_glyph_outline` costs about 65 tokens per node and has no summary mode; the legacy route can be stale after API writes and is only FLAGGED by v0.25+, not corrected (section 8i); the smooth gate checks the ROUNDED handles, so very short handles on smooth nodes may be refused (computed, not tried live).
- **New-font and guard limits (v9):** there is no create-font tool; the guard remembers only this listener run's changes and skips refreshes while anything is unsynced (the grid / glyph list may then lag until the person opens a glyph); server replies show the guard fields only from v0.27; nothing has been tested after a save and reopen (File > Save tests deferred by the user).
- **Test glyphs in the user's font (v8 record, probably gone):** `ltr88c` (180 nodes) and `ltr88k` (990 nodes), made after the last FontLab restart. Earlier prefixes of this session (`grd83a`, `stl85a`, `ltr86o`, `ltr86d`, `ltr87s`, `ltr87e`) were removed by FontLab restarts. A FontLab restart without saving removes them; `delete_glyph` asks for confirmation in FontLab. If FontLab was restarted since, they are gone. Use a NEW name prefix for the next round (v9 used `nfo9x`, `gd87x`; suggestion: `cmp91`). In v9 the disposable fonts were NEW "Unnamed Regular" fonts made with `flPackage()`, never saved; the state of the user's FontLab at hand-off is unknown.

- **Sync and new-font limits (v10):** the auto sync is proven for a new unsaved font and for a font opened from a file, on NEW glyphs, in a font with a single layer `test_font` / `Regular`; NOT proven for existing glyphs with legacy layers (T4), for a glyph whose editor tab is open (T3), for multi-layer glyphs, quadratic fonts, big glyphs, or after File > Save (deferred).
