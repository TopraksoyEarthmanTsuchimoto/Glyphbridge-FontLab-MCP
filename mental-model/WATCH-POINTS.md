# Watch points

What was seen in FontLab, in the tools or in agent behaviour and is **not yet explained or settled**. A proven fact belongs in its topic file, an open scenario in [CHECKLIST.md](CHECKLIST.md), a known limit in [ROADMAP.md](ROADMAP.md). Word budget: 2,500 ([MARKDOWN-MAP.md](MARKDOWN-MAP.md)).

## How an entry lives

- **Record:** the date first seen, the test numbers, what was seen, what is still open, and what would settle it.
- **Settle:** after a run that rules out the obvious alternative, move the fact to its topic file, delete the entry, and add one line to [archive/WATCH-POINTS-settled.md](archive/WATCH-POINTS-settled.md).
- **Drop:** when an experiment contradicts it or it no longer matters, delete it and add one line to the same archive file.
- **Keep it short:** an entry holds what is open and what would settle it; the evidence lives in the topic file it links to ([DECISIONS.md](DECISIONS.md), 2026-11-12).
- [CURRENT-STATUS.md](CURRENT-STATUS.md) shows only the number of open entries.

## FontLab and fonts

- **Whole-unit sidebearing shift** (2026-11-03, T4: 145c, 145f, 259, 260). `setSB` shifts by whole units (−52 for −52.1548; −142 on the element of `A`, fractions kept); facts: [topics/geometry.md](topics/geometry.md) §8c. Open: does the advance round to the nearest unit or up (382.534 → 383)? What does a plain contour with fractional nodes do? Settles: a target whose advance ends in .1 to .4. Candidate P2.8 in [ROADMAP.md](ROADMAP.md).
- **Identical font tabs** (2026-11-03, T5: 277–281, [LIVE-TESTS.md](LIVE-TESTS.md)). A `.vfc` and its Explorer copy got the same tab title and Fonts panel line; only the tab order told them apart. Open: does FontLab show the file name anywhere for a person to check? Agents should not ask the person to tell such fonts apart by title.
- **Legacy `font.info` against Font Info** (2026-11-03, 298, 300, 322–324; NM 845, 849). The legacy names lag behind Font Info: the family caught up after a later OK, the Full and PostScript names never did ([topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8k). Open: do they ever catch up (after a save; save tests by preference only)? Should the reply's font name come from the package when it can be matched?
- **Font Info's OK writes fields** (2026-11-03, 297, 298). `dict.names.keys()` went from 5 to 15 keys (Creator and Legal fields) after Font Info was closed with OK, with only the PostScript field edited. Open: does OK alone add them? Settles: open and OK without any edit.
- **Set or derived names** (2026-11-03, 298). Font Info shows a ↺ reset button beside Style name, Full name, PostScript and Style group, as if FontLab knew which were typed by a person; no read so far shows that ([DECISIONS.md](DECISIONS.md), design C). Font Info's OK did not derive those fields from a new family (843, 848); Build Names did (845, 849).
- **One `.notdef` warning for all unsaved fonts** (2026-11-03, 375, 376, [LIVE-TESTS.md](LIVE-TESTS.md) F1). The listener remembers a warned font by its path, and every unsaved font has an empty path. Open: is a second new font in one listener run never warned? Settles: two new fonts in one listener run, `get_current_font` on each.
- **The hover after a gated mark** (2026-11-03, S1: 460–472; 657–725; [topics/server-and-endpoints.md](topics/server-and-endpoints.md) §2). Open: why the icon needed a hover after the gated probe that followed a delete (686), while other marks turned it blue at once. Settled for kerning writes. Settles the rest: a repeatable condition for the probe, or `set_kerning` with the refresh switched off.
- **A dot after the glyph name in its tab** (2026-11-04, INK: 533; 2026-11-17, 1043a; [LIVE-TESTS.md](LIVE-TESTS.md)). Open: does the dot mark the glyph, the font, or a GUI selection? Settles: open an untouched glyph in a freshly opened font, then again after one tool write elsewhere.
- **A glyph's history after the notification** (2026-11-09, 661, 665, 668, 669, 686). The readings: [topics/server-and-endpoints.md](topics/server-and-endpoints.md) §2. Open: what `currentHistoryState` counts and what resets it. Settles: two calls on one glyph, and a first call after a restart.
- **The Add Component crash** (2026-11-09, 612–619). The fact is in [FONTLAB-API-RULES.md](FONTLAB-API-RULES.md) §9. Open: why a layerless `cp1comp` survived as the font's first component; multi-master fonts. Settles: Add Component on a layerless glyph as the first component of a new font, repeated.
- **The Elements badge** (2026-11-09, 606–635; 1042a, 1050a; [LIVE-TESTS.md](LIVE-TESTS.md)). It reads the number of uses plus one, also for uses placed by `buildAuto()`. Open: is it `referenceCount` (2 on a source, 1 on a component, 609, 610)? Settles: read the source after adding a use.
- **A tool edit of a source that misses its composites** (2026-11-09, 638–655). The fact and the runs: [topics/reading.md](topics/reading.md). Open: why `set_glyph_sidebearings` reached them once in five when GUI edits always did. Settles: a run that predicts which tool edit will reach them.
- **`componentsCount()`, `layer.components` and `clearComponents()` miss component shapes** (2026-11-09, 644–650; 2026-11-17, 1029, 1041b, 1049, RM 1246, one run; [topics/reading.md](topics/reading.md), "Components: removing one through the API"). On layers whose elements read `isComponent` true, `componentsCount()` reads 0 and `layer.components` an empty list; `layer.clearComponents()` changed nothing on a glyph of three components. Open: what kind of component those three count (a legacy or recipe list?). Risk: none known since listener 0.177, which counts components by `isComponent` (CC 1249, 1250c) and keeps `componentsCount()` as information and a guard only. Settles: a layer on which `componentsCount()` or `layer.components` reads more than 0, with what `clearComponents()` then does; or FontLab's documentation of the difference.
- **`setSB` as an element offset on a plain contour** (2026-11-09, 638). It put `dx` 200 on the element of `mx1dieresis` and left the nodes, unlike `testglyph2` (145c). Open: is it because the glyph is used as a component? Settles: `setSB` on the same outline in a glyph no component uses.
- **The Transform panel's X** (2026-11-09, 694, 699). With a Power Brush element offset by `setSB`, the Elements panel showed Δ=(6,0) and Δ=(-4,0) while the Transform panel's X read 0. Open: what that field shows. Settles: read it with the element selected, after a known move.
- **A GUI rebuild against a load rebuild** (2026-11-10, PB2 816, 821 against 799, 810, 820; [topics/reading.md](topics/reading.md) §8p). Settles: one stroke read after a GUI rebuild and again after a reload.
- **A rotated component's offset in whole units** (2026-11-10, 769; [topics/reading.md](topics/reading.md)). FontLab stored 38 / −43 for an exact 38.397 / −43.301; the read is right, since it uses the stored matrix. Open: does FontLab always round a transform's offset? Settles: a rotation whose exact offset ends in .5, and a scale about a corner with a fractional result.
- **The small element panel after a rotation** (2026-11-10, 768, 771; [LIVE-TESTS.md](LIVE-TESTS.md)). It showed 0 % after a 90° rotation, and in 771 a 30 % component became full size after X and Y were set there. Open: which edit dropped the scale; does the panel rebuild the matrix from the scale it shows? Settles: one field at a time, read after each.
- **The FONTS panel after an API name write** (2026-11-11, NM 855–918; evidence [topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8k). - **The grid selection after a mark** (2026-11-12, 913, 918–924; [LIVE-TESTS.md](LIVE-TESTS.md)). - **A later delete flattens a Power Brush glyph** (2026-11-14, DL 937–953). The fact is in [topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8l. Open: what arms the glyph. Settles: DL2, one variable per round, each from a fresh FontLab start. **PB series (2026-11-18, 1338–1345):** the guard's full check read `glyph.layers` and `glyph.layer` of a GUI-drawn brush glyph (tab closed) at six probe steps, two `font.update()` calls followed, and the brush stayed; so that read alone did not arm it here, and the second-update candidate did not flatten it either.
- **Sidebearings and ink box lag after an API edit** (2026-11-14 ED2 968–983; 2026-11-15 MN 1001–1023; 2026-11-17, 1043). - **A recipe's placement and width** (2026-11-17, 1049–1177; [topics/reading.md](topics/reading.md)). `buildAuto()` puts the first glyph at identity and moves each later one so that its ink centre lands on 0, the first glyph's advance in every run (1172 ruled out "half the ink width"); it set the width to 500 after every build, also when the ink was 600 wide (1138), so the ink-width explanation is dropped. - **What `killAuto()` does** (2026-11-17, 1055, 1074; [topics/reading.md](topics/reading.md)). On an auto layer `buildAuto()` had filled it returned None and changed nothing read, twice. Settles: a read or screenshot that differs after a call, or a docstring that says what it does.

Settles: a second occurrence with every step logged. **A second occurrence (2026-11-18, TL 1290–1291):** `cppnet2`'s component of `cppnes2` (placed by `add_component`, a recipe build) read as a plain shape at (300, 0) before `droptemp` (1290) ran; it was a component right after 1272. In between `cppnet2` kept an empty `gb_temp_component` as its active layer, its sync verdict `at_risk`; logged in between: listener restarts, `create_glyph cppnet5` (1273a), the probe on `cppnet3` / `cppnet4` (1274–1289), the person opening `cppnet4` (1284). The other recipe-built components (`cppnet1`, `cppnet3`, `cppnet4`) stayed components. Not isolated; a candidate: something synced or refreshed a glyph whose active layer was not its working layer. **The isolation run H1 (2026-11-18, 1301–1314):** H1 (`create_glyph`'s `font.update()` after a listener restart flattens the glyph whose empty temporary layer is active) predicted only `cppnet10`; `cppnet8`, `cppnet9` and `cppnet10` became plain shapes, the control `cppnet7` (a temporary layer added and dropped before any `create_glyph`) and the components of `cppnet1`, `3`, `4`, `6` did not. **Run C (2026-11-18, 1315–1327, every target read after every step)** repeated it and found the moment: the next `font.update()` that runs (1325). Flattened only a glyph that had, while its temporary layer was active, a `create_glyph` with a skipped refresh or a listener restart; not one whose temporary layer was added and dropped with nothing in between. Open: what in those two events arms it. Candidates from the code, untested: the guard's full check (`_guard_classify`) reads the legacy layers; the bridge builds a new `flGlyph` wrapper (the cache is empty after a restart), compare F1. Settles: a run that logs the outline reply's `wrapper` field at each step and changes one of the two.
