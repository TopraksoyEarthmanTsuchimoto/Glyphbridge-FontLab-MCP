# Watch points

What was seen in FontLab, in the tools or in agent behaviour and is **not yet explained or settled**. A proven fact belongs in its topic file, an open scenario in [CHECKLIST.md](CHECKLIST.md), a known limit in [ROADMAP.md](ROADMAP.md). Word budget: 2,200 ([MARKDOWN-MAP.md](MARKDOWN-MAP.md)).

## How an entry lives

- **Record:** the date first seen, the test numbers, what was seen, what is still open, and what would settle it.
- **Settle:** after a run that rules out the obvious alternative, move the fact to its topic file, delete the entry, and add one line to [archive/WATCH-POINTS-settled.md](archive/WATCH-POINTS-settled.md).
- **Drop:** when an experiment contradicts it or it no longer matters, delete it and add one line to the same archive file.
- **Keep it short:** an entry holds what is open and what would settle it; the evidence lives in the topic file it links to ([DECISIONS.md](DECISIONS.md), 2026-11-12).
- [CURRENT-STATUS.md](CURRENT-STATUS.md) shows only the number of open entries.

## FontLab and fonts

- **Whole-unit sidebearing shift** (2026-11-03, T4: 145c, 145f, 259, 260). `setSB` moved `testglyph2` by −52, not −52.1548 (its nodes moved), and the Power Brush glyph `A` by −142, not −142.466 (its element transform, fractions kept); the reply said `set: false` with its reason. Open: does the advance round to the nearest unit or up (382.534 → 383)? What does a plain contour with fractional nodes do? Settles: a target whose advance ends in .1 to .4. Details: [topics/geometry.md](topics/geometry.md) §8c; candidate P2.8 in [ROADMAP.md](ROADMAP.md).
- **Arial's `kern` feature against its table** (2026-11-03, K11). 1,417 `pos` lines against 1,370 table entries, although the 20 pairs compared agree.
- **FontLab 8.9.5 against 8.4.2** (since 2026-11-01). No difference seen. Writes seen on 8.9.5: `create_glyph`, `draw_polygon`, `set_glyph_width` and `set_glyph_sidebearings` on new glyphs (K9 setup, 190, 253) and on two existing glyphs (T4), a declined `delete_glyph` (190), `set_glyph_unicode` (280), `draw_path` (595–603), `set_kerning` (565–577) and a confirmed `delete_glyph` (683).
- **Identical font tabs** (2026-11-03, T5: 277–281). With a `.vfc` and its Explorer copy open, both tabs read "fullname of test font" and the Fonts panel listed "testfont" twice as "Regular"; only the tab order told them apart. Open: does FontLab show the file name anywhere for a person to check? Agents should not ask the person to tell such fonts apart by title.
- **Legacy `font.info` against Font Info** (2026-11-03, 298, 300, 322–324; NM 845, 849). The legacy names lag behind Font Info: the family caught up after a later OK, the Full and PostScript names never did ([topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8k). Open: do they ever catch up (after a save; save tests by preference only)? Should the reply's font name come from the package when it can be matched?
- **Font Info's OK writes fields** (2026-11-03, 297, 298). `dict.names.keys()` went from 5 to 15 keys (Creator and Legal fields such as `copyright`, `designer`, `vendor_code`) after Font Info was opened and closed with OK, with only the PostScript field edited. Open: does OK alone add them? Settles: open and OK without any edit.
- **Set or derived names** (2026-11-03, 298). Font Info shows a ↺ reset button beside Style name, Full name, PostScript and Style group, as if FontLab knew which were typed by a person; no read so far shows that ([DECISIONS.md](DECISIONS.md), design C). Font Info's OK did not derive those fields from a new family (843, 848); Build Names did (845, 849).
- **One `.notdef` warning for all unsaved fonts** (2026-11-03, 375, 376). The listener remembers a warned font by its path, and every unsaved font has an empty path. In 375 a new font got `already_warned` and no dialog from a listener that had run before; after a FontLab restart the dialog came (376). Open: is a second new font in one listener run never warned? Settles: two new fonts in one listener run, `get_current_font` on each.
- **The hover after a gated mark** (2026-11-03, S1: 460–472; 657–669, 686). Open: why the icon needed a hover after the gated probe that followed a delete (686), while it turned blue at once after a gated kerning mark (715) and after the built marks of 668, 669 and 688 ([topics/server-and-endpoints.md](topics/server-and-endpoints.md) §2). Focus alone was tried and dropped (725). For kerning writes it is settled ([archive/WATCH-POINTS-settled.md](archive/WATCH-POINTS-settled.md)). Settles the rest: a repeatable condition for the probe, or a run of `set_kerning` with the refresh switched off.
- **A dot after the glyph name in its tab** (2026-11-04, INK: 533). Opened from the grid with all nodes selected and nothing moved, the tab read "testglyph2•"; the only change in the font was `create_glyph w25a_one` (531). Open: does the dot mark the glyph, the font, or a GUI selection? Settles: open an untouched glyph in a freshly opened font, then again after one tool write elsewhere.
- **A glyph's history after the notification** (2026-11-09, 661, 665, 668, 669, 686). `currentHistoryState` and `initialHistoryState` moved together across new fonts, as if one counter ran across fonts, and `hasChanges` did not follow the icon; the readings: [topics/server-and-endpoints.md](topics/server-and-endpoints.md) §2. Open: what the number counts and what resets it. Settles: two calls on one glyph, and a first call after a restart.
- **The Add Component crash** (2026-11-09, 612–619). The fact is in [FONTLAB-API-RULES.md](FONTLAB-API-RULES.md) §9. Open: why a layerless `cp1comp` survived as the font's first component; multi-master fonts. Settles: Add Component on a layerless glyph as the first component of a new font, repeated.
- **The Elements badge** (2026-11-09, 606–615). It read 2, 3, 4 and 5 as uses of the source were added, as if counting them; `referenceCount` read 2 on the source and 1 on the component (609, 610). With one use it read 2, with two uses 3 (629, 635). Open: is it `referenceCount`? Settles: read the source after adding a use.
- **A tool edit of a source that misses its composites** (2026-11-09, 638–655). The fact is in [topics/reading.md](topics/reading.md). Open: why `set_glyph_sidebearings` reached them once (638) and missed four times (638b, 640, 648, 653), when GUI edits always did (639, 643, 652, 655); a non-zero offset was tried as the cause and dropped (640); `fontlab.Update` on the composite did not help (642); `isUnbindedDependecies()` did not change (647, 649). Settles: a run that predicts which tool edit will reach them.
- **`componentsCount` of 0** (2026-11-09, 644–650). The modern layer's `componentsCount` read 0 on `mx1Odieresis` and `mx1Udieresis`, whose two elements each read `isComponent` true. Open: what it counts. Settles: read it on a layer with a known component made another way.
- **`setSB` as an element offset on a plain contour** (2026-11-09, 638). It put `dx` 200 on the element of `mx1dieresis` and left the nodes, unlike `testglyph2` (145c); inside the composites that offset read as part of the component's coordinates. Open: is it because the glyph is used as a component? Settles: `setSB` on the same outline in a glyph no component uses.
- **The Transform panel's X** (2026-11-09, 694, 699). With a Power Brush element offset by `setSB`, the Elements panel showed Δ=(6,0) and Δ=(-4,0) while the Transform panel's X read 0. Open: what that field shows. Settles: read it with the element selected, after a known move.
- **A GUI rebuild against a load rebuild** (2026-11-10, PB2 816, 821 against 799, 810, 820). A brush stroke rebuilt in FontLab's GUI (drawn, or its brush size changed) had whole-unit extremes and a few fractional control points; rebuilt at load, every node had a fraction ([topics/reading.md](topics/reading.md) §8p). Open: does the GUI rebuild round where the load rebuild does not? Settles: one stroke read after a GUI rebuild and again after a reload, side by side.
- **A rotated component's offset in whole units** (2026-11-10, 769). Rotated 30° about the bottom-left corner of its box, (100, 50), a component needs an offset of 38.397 / −43.301; FontLab stored 38 / −43, so the result sits 0.397 / 0.301 away from an exact rotation about that corner. The read is right, since it uses the stored matrix. Open: does FontLab always round the offset of a transform? Settles: a rotation whose exact offset ends in .5, and a scale about a corner with a fractional result.
- **The small element panel after a rotation** (2026-11-10, 768, 771). After a 90° rotation it showed width and height 0 %. In 771 a component scaled to 30 % and rotated 90° by the Transform panel (Δ=(115,20), read as expected) became full size again, rotated, at (250, 80) after X 250 and Y 80 were set there, each with Enter (read: m11 0, m12 1, m21 −1, m22 0). Open: which of the two edits dropped the scale, and whether the panel rebuilds the matrix from the scale it shows. Settles: one field at a time, read after each.
- **The FONTS panel after an API name write** (2026-11-11, NM 855–914). A Font Info family change refreshes it at once (903) and a close usually rebuilds it from the current `tfn` (871, 880, 901); an add shows older names (894–900); evidence in [topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8k. Open: 896 and 914, where closes left a font's line at its creation name (both fonts were named in or right after their creation request), against 918, where a close refreshed a `create_font` font named in its request; a call that rebuilds without a close. Settled by: the 914 set-up repeated with a pause and a screenshot after the closes, and a Font Info edit of that font afterwards.
- **A tab's title** (2026-11-11, NM 878–910). It is a copy, refreshed only when the Full name is changed to a different value in Font Info (902, 907b, 910); no API write, `title_name` call (905, 908), empty OK (906), identical retype (907), add or tab switch (909) does it. Open: whether any API call acts like Font Info's own edit path. Settled by such a call after which the tab changes.
- **The grid selection after a mark** (2026-11-12, 913; again 918). After the package-level mark the `.notdef` cell lost its highlight and the counter read 0/1 instead of 1/1, on a font made by `flPackage()`; in 918 the marked `create_font` font read 0/1 and the unmarked one 1/1 (919), but marked fonts read 1/1 in 921 and 924, so the mark alone does not explain it. Open: does the mark do it, or focus? Settled by the same font, the mark, then a screenshot with the focus kept off the grid, and a control without the mark.
- **The legacy family reverted** (2026-11-11, NM 865, 872; 889–893). `font.info.familyName`, written and read back (865), read "Unnamed" again by 872, after another font was closed and the listener restarted; on the next such font it stayed as written through restarts and closes (890–893, [topics/fonts-and-sync.md](topics/fonts-and-sync.md) §8k). Open: what rewrote it; left from the run of 872 are four refresh calls (866–869) and Font Info closed with OK and no edit (870). Settled by a read after each of them.
- **Two "no font" states** (2026-11-11, 852). With no font open, `CurrentFont()` returned FontLab's placeholder font at the start of the FontLab run, and nothing later in the same run, after fonts had been opened and closed. The tools decide by `CountFonts()`, so neither affects them. Settled by reading both states in one run with a known history.
