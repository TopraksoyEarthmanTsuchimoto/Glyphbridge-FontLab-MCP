# Watch points

What was seen in FontLab, in the tools or in agent behaviour and is **not yet explained or settled**. A proven fact belongs in its topic file, an open scenario in [CHECKLIST.md](CHECKLIST.md), a known limit in [ROADMAP.md](ROADMAP.md). Word budget: 1,800 ([MARKDOWN-MAP.md](MARKDOWN-MAP.md)).

## How an entry lives

- **Record:** the date first seen, the test numbers, what was seen, what is still open, and what would settle it.
- **Settle:** after a run that rules out the obvious alternative, move the fact to its topic file and delete the entry.
- **Drop:** when an experiment contradicts it or it no longer matters, delete it and add one line to the record at the end.
- [CURRENT-STATUS.md](CURRENT-STATUS.md) shows only the number of open entries.

## FontLab and fonts

- **Whole-unit sidebearing shift** (2026-11-03, T4: 145c, 145f, 259, 260). `setSB` moved `testglyph2` by −52, not −52.1548 (its nodes moved), and the Power Brush glyph `A` by −142, not −142.466 (its element transform, fractions kept); the reply said `set: false` with its reason. Open: does the advance round to the nearest unit or up (382.534 → 383)? What does a plain contour with fractional nodes do? Settles: a target whose advance ends in .1 to .4. Details: [topics/geometry.md](topics/geometry.md) §8c; candidate P2.8 in [ROADMAP.md](ROADMAP.md).
- **`updated_fg_glyphs` after a write** (2026-11-03, T4: 145b, 145e). The probe's list went from 0 to 4 ids after the width write on `testglyph2`, and held 1 id after the width write on `A`. Not predicted; no tool depends on it.
- **Arial's `kern` feature against its table** (2026-11-03, K11). 1,417 `pos` lines against 1,370 table entries, although the 20 pairs compared agree.
- **FontLab 8.9.5 against 8.4.2** (since 2026-11-01). No difference seen. Writes seen on 8.9.5: `create_glyph`, `draw_polygon`, `set_glyph_width` and `set_glyph_sidebearings` on new glyphs (K9 setup, 190, 253) and on two existing glyphs (T4), a declined `delete_glyph` (190), and `set_glyph_unicode` (280). The other writes: not yet.
- **Identical font tabs** (2026-11-03, T5: 277–281). With a `.vfc` and its Explorer copy open, both tabs read "fullname of test font" and the Fonts panel listed "testfont" twice as "Regular"; only the tab order told them apart. Open: does FontLab show the file name anywhere for a person to check? Agents should not ask the person to tell such fonts apart by title.
- **Legacy `font.info` against Font Info** (2026-11-03, 298, 300). After the PostScript field was set to `W6aTest-Regular`, `font.info.postscriptFontName` still read `Unnamed1-Regular` while the package's `psn` read the new value. The family name lags too (322–324): after Unnamed1's Family name was set to `Unnamed`, the replies kept "Unnamed1 Regular" across two tab switches, while the Fonts panel listed "Unnamed (2 fonts)" (323). Open: does the legacy view ever catch up (after a save; save tests by preference only)? Should the reply's font name come from the package when it can be matched?
- **Font Info's OK writes fields** (2026-11-03, 297, 298). `dict.names.keys()` went from 5 to 15 keys (Creator and Legal fields such as `copyright`, `designer`, `vendor_code`) after Font Info was opened and closed with OK, with only the PostScript field edited. Open: does OK alone add them? Settles: open and OK without any edit.
- **Set or derived names** (2026-11-03, 298). Font Info shows a ↺ reset button beside Style name, Full name, PostScript and Style group, as if FontLab knew which were typed by a person; no read so far shows that ([DECISIONS.md](DECISIONS.md), design C).
- **One `.notdef` warning for all unsaved fonts** (2026-11-03, 375, 376). The listener remembers a warned font by its path, and every unsaved font has an empty path. In 375 a new font got `already_warned` and no dialog from a listener that had run before; after a FontLab restart the dialog came (376). Open: is a second new font in one listener run never warned? Settles: two new fonts in one listener run, `get_current_font` on each.
- **Why tool changes raise no save question** (2026-11-03, S1: 460–472). The fact is in [topics/server-and-endpoints.md](topics/server-and-endpoints.md) §2. Guess: API writes do not set FontLab's "changed" flag. The icon before the font name in the font window's title was blue after a GUI change (469) and stayed dark after a tool write (471c); that it is the flag is not proven. Kerning writes behave the same: icon not blue, no save question on close (561–577). Open: do drawings, sidebearings and deletes behave the same? Can the API set the flag without saving (`flLayer` lists `isChanged`, `hasChanges` and `changed`, 478, names only)? Settles the guess: `/debug/trysync?stage=state` (read-only, `isChanged` of the package) before and after one tool write, then after one GUI change.
- **A dot after the glyph name in its tab** (2026-11-04, INK: 533). Opened from the grid with all nodes selected and nothing moved, the tab read "testglyph2•"; the only change in the font was `create_glyph w25a_one` (531). Open: does the dot mark the glyph, the font, or a GUI selection? Settles: open an untouched glyph in a freshly opened font, then again after one tool write elsewhere.
- **The package's change flags stay false** (2026-11-04, KW: 553–556). `flPackage.isChanged` and `hasChanges` read false in a new font changed through the tools, by an API kerning write and by a GUI kerning edit; the kerning container's flags moved (`changed()`, `Update`). One font, one session. Open: what FontLab's "modified" state reads from, and whether it relates to S1. Settle by reading the flags before and after a GUI glyph edit that makes FontLab ask on close.
- **The Add Component crash** (2026-11-09, 612–619). The fact is in [FONTLAB-API-RULES.md](FONTLAB-API-RULES.md) §9. Open: why a layerless `cp1comp` survived as the font's first component; multi-master fonts. Settles: Add Component on a layerless glyph as the first component of a new font, repeated.
- **The Elements badge** (2026-11-09, 606–615). It read 2, 3, 4 and 5 as uses of the source were added, as if counting them; `referenceCount` read 2 on the source and 1 on the component (609, 610). With one use it read 2, with two uses 3 (629, 635). Open: is it `referenceCount`? Settles: read the source after adding a use.
- **A tool edit of a source that misses its composites** (2026-11-09, 638–655). The fact is in [topics/reading.md](topics/reading.md). Open: why `set_glyph_sidebearings` reached them once (638) and missed four times (638b, 640, 648, 653), when GUI edits always did (639, 643, 652, 655); a non-zero offset was tried as the cause and dropped (640); `fontlab.Update` on the composite did not help (642); `isUnbindedDependecies()` did not change (647, 649). Settles: a run that predicts which tool edit will reach them.
- **`componentsCount` of 0** (2026-11-09, 644–650). The modern layer's `componentsCount` read 0 on `mx1Odieresis` and `mx1Udieresis`, whose two elements each read `isComponent` true. Open: what it counts. Settles: read it on a layer with a known component made another way.
- **`setSB` as an element offset on a plain contour** (2026-11-09, 638). It put `dx` 200 on the element of `mx1dieresis` and left the nodes, unlike `testglyph2` (145c); inside the composites that offset read as part of the component's coordinates. Open: is it because the glyph is used as a component? Settles: `setSB` on the same outline in a glyph no component uses.
- **Two GUI events** (2026-11-09). Editing X, Y and width of a component together changed nothing and left its source glyph in front; each field alone worked. One Font > New Glyph added no glyph. Neither repeated.

Inferred: the server process outlives the sessions. Not checked in the process list.
