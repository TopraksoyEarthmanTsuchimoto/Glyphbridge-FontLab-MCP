## 8p. Kerning: how it is read (research v0.90 to v0.93, tool listener 0.94 / 0.95, server 0.30 / 0.31; the whole path is described here because it is the persistent record)

**Note (2026-11-01):** from listener 0.104 / server 0.33 the route reads the current master's table with explicit keys (§10). The `font.kerning.get` path below is that of listeners 0.94 to 0.103.

**Goal and standing rule (user, 2026-10-25).** Agents must be able to read and inspect kerning, **without reading the whole table or the whole font**: a few selected glyph pairs, to save tokens. Everything below follows from that rule.

**Fact to keep for agents:** in Arial's table the accented capitals `Aacute`, `Adieresis` against `V` gave NO entry although `A : V` is -152. `get` answers what FontLab's kerning table holds for exactly those two glyph names (plus classes); an agent must not assume an accented glyph inherits its base glyph's direct pairs. Whether FontLab's TEXT RENDERING applies kerning to such pairs through another mechanism (for example OpenType `kern` feature code) was checked for Arial in K10 (test 224): a text line applies no kerning to Á V either; OpenType feature code stays open (K11). Since listener 0.104 the tool reads the current master's table (`flPackage.kerning`) instead of `font.kerning`; on Arial it gives the same answers, `Aacute : V` included (tests 191, 222, §10).

**5. The product: listener `GET /kerning/pairs` (0.94) and `POST /kerning/pairs` (0.95), function `get_kerning_pairs(pairs, text)`.**
- **No font:** `CountFonts() == 0` (checked FIRST; this route uses the correct "open" test of section 8k) or `CurrentFont() is None` answers `{"open": false}` and `CurrentFont()` is not even asked when `CountFonts()` is 0.
- **Glyph names must exist** (the glyph set is read from `font.glyphs`); an unknown name gives that pair an `error` ("no glyph named 'Q'") and the other pairs are still read.
- **Text mode:** every character is mapped to the ONE glyph whose PRIMARY Unicode (`glyph.unicode`, plain int) is that code point; a character with no glyph, or with several glyphs (the reply lists up to 5), gives each pair it belongs to an `error`; glyphs whose Unicode could not be read are counted and named in the error ("no proof that none has it"). The neighbours of the text are the pairs (a text of n characters has n - 1 pairs, `chars` shows the two characters). Secondary Unicodes are not looked at.

**6. The product: server tool `get_kerning` (v0.30, v0.31), function `read_kerning(pairs, text, confirmed_large_read)`.**
- **Approval threshold (v0.31, `_KERN_CONFIRM_ABOVE = 250`):** a request for MORE than 250 pairs (for text: more than 251 characters) with `confirmed_large_read` not exactly `True` is refused before sending, with the message "This request would read N kerning pairs, more than the 250-pair threshold, and nothing was read. Do NOT repeat the call yet. A large read costs many tokens: tell the person how many pairs you want to read and why, and ask whether they approve. Only after they have said yes, call get_kerning again with the same arguments and confirmed_large_read=true. Never set that flag without the person's approval." Name validation comes first, then the threshold. Exactly 250 pairs needs no approval; the flag on a small request is accepted and ignored. The flag is the agent's own claim: **a tool cannot verify that a human said yes** (decided and told to the user in the proposal).

**8. Not covered (current).** Feature-based (GPOS) and contextual kerning, and the other masters of a multi-master font, are not read or written. "All pairs of one glyph" is deliberately not offered (it would read the whole table). The KERNING panel's filter also matches group members, on both sides, so a missing row means the table has no entry for that pair, direct or through a group (166–167). Text with a character that several glyphs share as primary Unicode is stub-tested only.

## 9. Two kerning tables and a name collision (2026-11-01, tests 168–176, listener 0.97, FontLab 8.9.5)

**Stage:** a new disposable font with glyphs `kn1L`, `kn1R`, `kn1S` (boxes, width 500), a right kerning class holding `kn1R` and `kn1S`, a class pair `kn1L : class` -100, and later an exception `kn1L : kn1R` -50, all made in FontLab's GUI. Rebuild recipe: [LIVE-TESTS.md](../LIVE-TESTS.md), after the K-series table. FontLab applied both values on screen (the boxes touch at -100; a 50-unit gap at -50).

**1. Where the kerning lives (probe 171, names only; tests 172–176).** `flPackage` has `kerning`, documented as `fgKerning kerning([string master_name])`, plus `masters` (`QList<string>`), `master` (string) and `getAllGroups()`, documented as `list((bool kernGroup, string groupName, int id, int mark, list(string glyphName)))` (the candidate source for P1.6). Not called: `getAllGroups`, `findGroup`, `kerningContainer`, and the writing members `autoKern`, `deleteGroups`. `flPackage.kerning("Regular")` returns an `fgKerning` that held the GUI's pairs (`len` 1, then 2 with the exception), while the legacy `font.kerning` stayed `len` 0 and answered `None`. Its `get` resolves classes like the legacy one (`kn1L:kn1S` -100 through the class). No read changed either table (`side_effect_detected` false).

**2. Defect A: `get_kerning` reads the wrong table for GUI-made kerning.** It reads `font.kerning`, so in this font it answered 0 / `kerned` false for both pairs and "table_size is 0: this font has no kerning at all" (169) while FontLab applied -100. Switching to the font window tab did not change it (170). For Arial, loaded from a file, the legacy table is filled and K2–K8 match the panel. Not known: whether a GUI edit made after a file is loaded reaches the legacy table, and which master the tool should read in a multi-master font.

**3. Defect B: a glyph name that is also a class name is read as the class.** FontLab names a new class after its first member (`kn1R`; Arial does the same: `v`, `Aring`, `e`). With the class named `kn1R`, `get(("kn1L", "kn1R"))` on the master's table returned the class value -100 although the exception -50 existed (`len` 2) and FontLab applied it (174). After renaming the class to `kn1grp` (the only change), the same call returned **-50** (176). So exceptions win when names are unambiguous (the K9 question), and `get` with a plain name tuple prefers a class of that name. Proven on the right side here and on the left side in test 195 (point 8). A class member without an exception is not affected (its class value is its real value). How a caller says "glyph": point 6.

**6. Asking for a glyph or a group (tests 177–188, listener 0.98 to 0.100, the K9 font with the class named `kn1R`).**
- In `get(((a, flag), (b, flag)))` the flag means **"this name is a group"**: `((kn1L, False), (kn1R, False))` gave **-50**, the exception FontLab applies (186); `((kn1L, False), (kn1R, True))` gave -100, the class `kn1R` (187).
- `((kn1L, False), (kn1S, False))` gave **`None`** while FontLab applies -100 through the class (188): False / False matches only an exact glyph : glyph entry and does not resolve class membership.

**8. Precedence and the left side of defect B (tests 192–197, 2026-11-01, listener 0.102, FontLab 8.9.5, P0.8 step (c)).** **Stage:** a new disposable font with glyphs `kc1A`, `kc1B`, `kc1C`, `kc1D` (boxes, width 500, made through the tools), a left class {`kc1A`, `kc1B`} and a right class {`kc1C`, `kc1D`} (FontLab named them `kc1A` and `kc1C`; renamed `kc1lft` and `kc1rgt`), the class pair `kc1lft : kc1rgt` -100 and the exception `kc1A : kc1rgt` -50 (left side a glyph, made with Ctrl + Left arrow). ## 10. The fix (listener 0.104 / server 0.33, 2026-11-01, P0.8)

**How it reads.** `/kerning/pairs` reads `flPackage.kerning(current master)`, never the legacy `font.kerning` (defect A). With one font open the workspace's current package is the current font; since listener 0.112, with several fonts open, it is used only when its `path` is not empty and equals the current font's path, otherwise the request is refused with the reason (§12). A glyph's classes come from its `kerningLeft` / `kerningRight` group ids, named by ONE `getAllGroups()` per request when an id is not 0 (§9.9). Each pair is asked with explicit keys in FontLab's order, the first entry that exists answers: `((a,F),(b,F))`, `((a,F),(Rclass,T))`, `((Lclass,T),(b,F))`, `((Lclass,T),(Rclass,T))` (defect B: no plain name tuple is sent). Each result carries `source` (`glyph : glyph`, `glyph : class`, `class : glyph`, `class : class`, `none`) and the class names that answered; the reply carries `master` and `master_count`. An entry that holds 0 keeps its source; an unreadable, unlisted or twice-listed class id is an error for that pair. The server needs listener 0.104, checks every source and class name, and tells the agent to report the source and never guess. Timeout `5 + pairs/50` s.

- **Not covered:** other masters, GPOS and contextual kerning, timings on other fonts and machines (K14 measured Arial only), two unsaved fonts (both paths empty: refused), a font opened twice (never tested; §12 does not cover it).

## 14. The write tool `set_kerning` (listener 0.124 / server 0.44, 0.45, 2026-11-04; live-checked 565–577)

**What it does.** `set_kerning(pairs=[[left, right, value], ...])` writes glyph : glyph entries into the current master's table of the font in front, with `set(((left, False), (right, False)), float(value))`, the `flags` form of 564: it names both sides as glyphs, so a glyph named like a class never means the class (defect B, §9). The font and table are matched exactly as `get_kerning` matches them (§10, §12); the read and the write share the matching and the effective-value lookup.

**Checks before any write** (a failed one refuses the whole request, nothing set): names are glyphs of the font (until listener 0.194 / server 0.78 class names were not accepted; since then a side written `@name` is a kerning group, §17), each pair once, values finite with |value| ≤ the package's `upm`, the master and `set` reachable. More than 250 pairs need the person's approval (`confirmed_large_write`), as for reads.

**Per pair, in order:** the effective value before (value and source, as `get_kerning` gives it) and the exact entry; one `set`; the exact entry and the effective value again. A pair is `set` only when the exact entry equals the value and FontLab applies it from the glyph : glyph entry. The first pair that is not set stops the request; the pairs after it are `not attempted`, and the error names the pairs that were set. `exception_over_class` marks a pair whose value came from a class before. `len()` is read before and after; growth other than the new entries is reported as a warning.

**What every reply tells the agent to say** (from §13): the KERNING panel, when the refresh below was not made, shows the pair only after a switch to another font and back or a save and reopen (557–560, 573); closing the font unsaved loses it, and with no mark (a listener older than 0.134, or `save_question_note` in the reply) FontLab asks no save question first (561, 562); Edit > Undo cannot take it back. To revert the write, restore a prior glyph : glyph value with `set_kerning`; if `before` was `none` or a class value, call `remove_kerning` to remove the new glyph : glyph entry and restore the prior state. Setting a pair to 0 leaves an explicit zero entry. Other masters and feature-based kerning remain uncovered; class entries are written since listener 0.194 / server 0.78 (§17); pair removal is built in §16.

**Server 0.45** turns these results into the tool: a value that is not a whole number is refused before sending; the reply says the panel shows new pairs and new values only after a switch to another font and back, or a save and reopen; a failed pair that changed names its current value; the reply carries `matched_by`. Live-checked (575, 576): 12.4 refused before anything was sent; a pair set with `matched_by` and the new panel wording in the reply. 577: after a `set_kerning` write, File > Save As, close and reopen: the panel lists the pair and `get_kerning` reads it; a tool write is saved like a GUI pair.

**The mark in the product (listener 0.134 / server 0.54, 2026-11-10, live 718–721).** A write that changed an entry makes this call itself, on the left glyph of the first changed pair, then its right glyph, then the sides of later changed pairs, never `.notdef`, at most 20 tried (`fontlab_changed_mark`, `via_glyph`). `set_kerning` alone turned the icon blue, after a hover, and FontLab asked (718, 719); the same value made no call and stayed dark (720); both pairs survived a reopen (721). The fallback to other glyphs is stub-tested only. Since server 0.55, when no entry changed the reply says so instead of warning about closing (720), and when the mark was made it tells the agent to say, once per package, that FontLab's icon may stay dark until the mouse moves near the font's title (719, 722, 723, 725, 726 needed a hover, 724 did not; retired in server 0.57, [DECISIONS.md](../DECISIONS.md)). Live-checked for 0.55: 727, 728.

## 15. The read tool `get_kerning_groups` (listener 0.190 / server 0.75, 2026-11-19, P1.6; live KGL 1376–1379)

**The design** (the user's six answers of 2026-11-19, [DECISIONS.md](../DECISIONS.md)): a tool of its own; named groups and / or glyphs, or every group, with approval above 250 groups; members always included; kerning groups only; every read cross-checked; an unknown name is an error for that name only.

**How it reads** (research §9.10): the font and master as `/kerning/pairs` (§10, §12); then ONE `items()` on `flPackage.kerning(master).groups` (name, members, side) and ONE `flPackage.getAllGroups()` (name, id, members, kerning flag), and nothing else; the sizes of the table and of the group container before and after. Only real lists and tuples are looked into. Sides: `KernLeft` → `left` (the group's glyphs as the LEFT glyph of a pair, the glyph's `kerningLeft`, §9.9), `KernRight` → `right`, `KernBothSide` → `both`; any other word → `unknown`, never confirmed.

**The cross-check:** a group is `confirmed` only when both sources name it, with the same members (order aside), the kerning flag true, and neither lists its name twice. Otherwise it is reported with `mismatch` (and `class_list_members` when the members differ); a group found only in the class list is reported with side `unknown`. A class list that cannot be read leaves every group unconfirmed (`cross_check` says why); `items()` that cannot be read refuses the whole read. In a font with no kerning group `getAllGroups()` returns `None` (1531); until listener 0.216 `cross_check` then read "failed" although the answer was right (AG2 1927, 1930). Since 0.217 one shared reader reads `None` as no groups for every caller, so the cross-check runs (stub-tested only). A glyph's groups are found in either source.

**Names:** a group name that is a class but not a kerning group (an OpenType class or a tag) gets its own error; a glyph in no kerning group gets a note, not an error.

## 16. Removing a pair (research, listener 0.191, 2026-11-19; live KD 1381–1390, KDC 1391–1397)

**Live (KD 1381–1390, one run each, a new unsaved font, one master, one font open; [LIVE-TESTS.md](../LIVE-TESTS.md)).**
- **`remove` deletes exactly one glyph : glyph entry, in both forms:** `(a, b)` (1383, 1390) and `((a, False), (b, False))` (1387). ## 18. Renaming and removing a group (research, listener 0.199, 2026-11-20; names only GE0 1499–1504, live GE 1505–1522)

**Research question.** Can a kerning group be renamed or removed through the API, and what happens to its class entries and to FontLab's view of it? Creating a group and changing its members are not covered here: their only candidate is a subscript assignment on `fgKerningGroups` ([LIVE-TESTS.md](../LIVE-TESTS.md), GE0).

**Names only (GE0).** The master's group container (`flPackage.kerning(master).groups`, an `fgKerningGroups`) documents `rename('oldGroupName', 'newGroupName')` → `bool/Nothing` and `remove('groupName'[, deleteDependentKerningPairs = false])`. The legacy `fgKerning` group calls have no docstrings; `flPackage` has `deleteGroups(ids, deleteDependentContent)` and no setter.

**Live (GE, one run each, a new unsaved font, one master).**
- **`rename` works in FontLab's data:** it returned `True`; the group under the new name has the same members and side, both sources confirm it, and its class entry answers under the new name only (1511, 1513). **The id changes** (5140 → 5142): an id is not a stable handle for a group across a rename.
- **`remove(name)` keeps the pairs by turning them into glyph pairs:** the group left both sources, the table kept its size, and the class entry `kge1 : kgeR` became the glyph entry `kge1 : kge3` (−40, `glyph : glyph`), shown as a plain row in the KERNING panel (1518, 1521, 1522). **One glyph pair per member:** a two-member group's class entry became two glyph pairs with the class value, table 2 → 3 (GL 1530, 1533). **What `remove(name)` makes of each kind of entry** (GK 1539–1545): a `class : glyph` or `glyph : class` entry becomes one glyph pair per member; a `class : class` entry against the removed group becomes one `class : glyph` (or `glyph : class`) entry per member of the removed group, and member pairs that already had a glyph entry keep it; a Kerning both group's entries on either side become glyph pairs of its member.
- **`remove(name, True)` deletes the group's entries:** the group's one entry went, table 2 → 1 (1520, 1522).
- **FontLab's view lags.** After a rename the Classes panel kept the old name (its member area empty when selected) and the KERNING panel the old label (1514); the glyphs kept the old group id, so `get_kerning` answered errors for the members (1512, after a removal 1519). A switch to another font and back brought the panels and the glyph ids up to date (1515, 1516, 1521, 1522). **So did one `notifyPackageContentUpdated(<package fgId>)`, the refresh `set_kerning` makes (§14), without a font switch, after a rename** (GR 1527–1529, [LIVE-TESTS.md](../LIVE-TESTS.md)): `get_kerning` read the members at once, and both panels showed the new name. After a removal it did the same (GL 1532–1534).
- **A rename onto a taken name** is refused by the probe before any call (1517); FontLab's own behaviour for it was not tried.
- **Not checked:** removing the left group of a class : class pair (presumably symmetric); the mark and FontLab's save question (the probe makes no mark; Demo mode cannot save); Edit > Undo; other masters; several fonts; class : class entries; a Kerning both group.

**The product tools** built on this research, and their live checks: §19.

*Moved to [archive/kerning-research.md](../archive/kerning-research.md) §18 (2026-11-26):* the probe.

## 19. The tools `rename_kerning_group` and `remove_kerning_group` (listener 0.200 / server 0.82, 2026-11-20; live GT 1546–1576)

**The design** ([DECISIONS.md](../DECISIONS.md), 2026-11-20): one group per call; `pairs` (`keep` or `delete`) required for a removal; a Yes/No dialog in FontLab for a removal only; a new name of any group or class refused, a glyph's name allowed with `same_name_glyph`; after a change the mark through one member, ONE `notifyPackageContentUpdated(<package fgId>)` (§14, §18) and `fontlab_caught_up`. Routes and replies: [server-and-endpoints.md](server-and-endpoints.md); the build: [CHANGELOG.md](../CHANGELOG.md).

**Live (GT, [LIVE-TESTS.md](../LIVE-TESTS.md), one run each, a new unsaved font, one master).**
- **Rename:** verified by both sources with the same members and side; the class entries followed the new name; `caught_up` true each time, and the Classes and KERNING panels and `get_kerning` showed the new name at once, with no font switch (1553–1555). A member's name as the new name worked, with the note (1556, 1559). Renaming back is the undo (1558, 1560).
- **Remove:** No changed nothing (1566, 1567); Yes with `keep` left the kerning as a glyph pair (table 2 → 2, 1568, 1569); Yes with `delete` deleted the group's entry (table 2 → 1, 1570, 1571); the panels followed at once (1572).
- **Refusals before any change or dialog:** a new name that is a kerning group's or an OpenType class's name, an OpenType class or an unknown name as the group, and two unsaved fonts open (1561–1565, 1574).
- **Ids:** every rename changed the id, as designed; the id seemed to follow the name (`kgrL` got 5154 each time; `kgr1` 5149, `kgr2` 5150), not explained ([WATCH-POINTS.md](../WATCH-POINTS.md)).
- **The client's time limit:** Claude Code ended the removal call of 1566 after 60 s while FontLab's dialog still waited (the server waits up to 120 s); the dialog's answer came later and changed nothing, since it was No ([WATCH-POINTS.md](../WATCH-POINTS.md), [ROADMAP.md](../ROADMAP.md)).

**Not checked live:** the save question for a group edit alone (Demo mode; the classes were made in the GUI, which already marks the font), Edit > Undo, other masters, a Kerning both group, a saved font beside others, more than eight members in the dialog.
