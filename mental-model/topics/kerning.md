## 8p. Kerning: how it is read (research v0.90 to v0.93, tool listener 0.94 / 0.95, server 0.30 / 0.31; the whole path is described here because it is the persistent record)

**Note (2026-11-01):** from listener 0.104 / server 0.33 the route reads the current master's table with explicit keys (§10). The `font.kerning.get` path below is that of listeners 0.94 to 0.103.

**Goal and standing rule (user, 2026-10-25).** Agents must be able to read and inspect kerning, **without reading the whole table or the whole font**: a few selected glyph pairs, to save tokens. Everything below follows from that rule.

**The font used:** Arial opened from the system (`path` `:/Arial: Normal`, 4548 glyphs, upm 2048, ascender 1491, descender -431, family `Arial`, style `Regular`, PostScript name `ArialMT`). FontLab 8.4.2.8950.

**2. What `font.kerning.get((a, b))` returns (gated probe `/debug/trykern`, listener 0.92; tests 150, 151, 154b; compared with the user's screenshots of FontLab's KERNING panel).** It returns a **float**, or **`None` for "no kerning entry"**; it does not change the table (`len` 1370 before and after, every call). The value is FontLab's own and **includes class (group) kerning on both sides**. Observed (font units, Arial upm 2048):

| pair (left : right) | `get` | note |
|---|---|---|
| A : V | -152.0 | direct pair |
| V : A | -152.0 | direct pair (150; the user confirmed the panel numbers match) |
| T : o | -227.0 | direct pair |
| A : B | None | "no kerning or 0 kerning" (user, panel) |
| Aacute : V | None | observed 151: an accented A does NOT inherit the direct pair A : V |
| Adieresis : V | None | 151 |
| T : oacute | None | 151 |
| T : odieresis | None | 151 |
| A : Wgrave.c2sc | -76.0 | glyph against the RIGHT group `@W.c2sc2` (154b) |
| Aacute : Wgrave.c2sc | -76.0 | LEFT group `@Aring` against the right group (group against group) |
| Atilde : Ydieresis.c2sc | -152.0 | `@Aring` against `@Y.c2sc2` (group against group) |
| A : Tbar.c2sc | -80.0 | glyph against a right group |
| Aacute : Tbar.c2sc | -80.0 | left group against a right group |

The user's reading of the panel ("some pairs are kerned directly, some against groups") was right. The probe accepts glyph names only (152: a group name such as `W.c2sc2` is refused by the probe: "no glyph with this name ... (group names are not accepted yet)"; the product tool does the same). Group names in the compiled text carry an `@` (for example `@Aring`, `@W.c2sc2`, `@Y.c2sc2`, `@Tcaron`).
**Fact to keep for agents:** in Arial's table the accented capitals `Aacute`, `Adieresis` against `V` gave NO entry although `A : V` is -152. `get` answers what FontLab's kerning table holds for exactly those two glyph names (plus classes); an agent must not assume an accented glyph inherits its base glyph's direct pairs. Whether FontLab's TEXT RENDERING applies kerning to such pairs through another mechanism (for example OpenType `kern` feature code) was checked for Arial in K10 (test 224): a text line applies no kerning to Á V either; OpenType feature code stays open (K11). Since listener 0.104 the tool reads the current master's table (`flPackage.kerning`) instead of `font.kerning`; on Arial it gives the same answers, `Aacute : V` included (tests 191, 222, §10).

**3. Group membership is NOT needed for the values, and `getCompiled()` is a dead end (probes 153, 154a; `/debug/trygroups`, listener 0.93).** `font.groups.getCompiled()` returns ONE string (38,853 characters, 132 lines, 132 segments) with lines like `@Aring=[AacuteAbreve Acircumflex Adieresis Agrave Amacron Aogonek Aring Aringacute Atilde];`. Problems found: (a) **the FIRST and SECOND member of a group are glued together without a separator** (`AacuteAbreve`, `Tcaronuni0162`, `W.c2scWacute.c2sc`); (b) it lists ALL 132 groups of the font, kerning groups mixed with OpenType classes and other groups (`@c2sc5=[ampersandA B C ...]`), with no side information (left / right / class kind); (c) `font.kerning.groups` has only 72 groups, so the 132 cannot be just the kerning groups (an inference; the two objects were not compared name by name). It is NOT parsed by anything in the product. Group membership could be read from `font.kerning.groups` (an `fgKerningGroups`), but that object was never probed beyond its length and is not needed for the tool.
Sample (154a): `@W.c2sc2=[W.c2scWacute.c2sc Wcircumflex.c2sc Wdieresis.c2sc Wgrave.c2sc]`, `@Y.c2sc2=[Y.c2scYacute.c2sc Ycircumflex.c2sc Ydieresis.c2sc Ygrave.c2sc]`, `@Tcaron=[Tcaronuni0162]`.

**4. The research probes (listener 0.90 to 0.93, all kept; names-only before gated; each tested with a forbidden-member spy and a static scan of its source).**
- `GET /debug/fontdir?stage=dir|sub|member[&attr=NAME][&members=a,b,c]` (0.90 `dir` / `sub`, 0.91 `member`): NAMES ONLY. `dir` lists the public names of the font object, `sub` the type, `len`, docstring and public names of ONE attribute (`attr`), `member` the type, callability, `len` and docstring of at most 8 named members of that attribute; it NEVER calls a member (`called: false`) and reads only the one attribute.
- `GET /debug/trykern?a=NAME&b=NAME&go=yes` (0.92): one `font.kerning.get((a, b))`; `go=yes` exactly; both names must be glyph names of the current font; `_TRYKERN_MAX = 20` calls per listener run (counted BEFORE the call); needs `CountFonts() >= 1`; reports `value_type`, `value`, `call_error`, `len_before`, `len_after`, `side_effect_detected`.
- `GET /debug/trygroups?go=yes[&contains=a,b,c]` (0.93): ONE `font.groups.getCompiled()`; `_TRYGROUPS_MAX = 10` per listener run; with no `contains` it returns the first 500 characters and the sizes; with up to 3 whole-word names it returns only the matching segments (at most 20, each cut at 300 characters), never the whole text.
These probes stay as evidence tools; the product tool does not need them.

**5. The product: listener `GET /kerning/pairs` (0.94) and `POST /kerning/pairs` (0.95), function `get_kerning_pairs(pairs, text)`.**
- **Verified read, so NO `go` gate and NO per-run counter** (a read-only call that was proven harmless in 150 to 154b). The ONLY member of the kerning object it ever touches is `get`, once per pair (spy test: every other member, among them `set remove clear addGroup deleteGroup renameGroup scale setPlainPairs asDict getPlainPairs getPlainPairsDict items keys values has_key hasGroupKerning groups`, aborts the test; a static scan of the function source checks the same).
- **Input: exactly one of** `pairs` or `text`. `pairs`: GET `?pairs=A:V,T:o` (a string; `:` and `,` cannot occur in glyph names), POST body `{"pairs": [["A","V"],["T","o"]]}`; 1 or more pairs; each name 1 to 63 characters from `A-Za-z0-9._-`, whitespace around a name is stripped. `text`: GET `?text=...` (percent-encoded UTF-8; a `+` is a space), POST body `{"text": "..."}`; 2 or more characters, no control characters (code points below 32 and 127 to 159 are refused; U+00A0 is allowed). **No upper limit in v0.95** (v0.94 allowed 40 pairs / 41 characters; the cap was removed by the user's decision). Bad input answers HTTP 400 with `{"error": ...}`; an unexpected exception answers 500; a POST body must be a JSON object with only the keys `pairs` and `text` (anything else, a non-list `pairs`, a non-string `text`: 400), invalid JSON or invalid UTF-8: 400 "request body was not valid JSON".
- **No font:** `CountFonts() == 0` (checked FIRST; this route uses the correct "open" test of section 8k) or `CurrentFont() is None` answers `{"open": false}` and `CurrentFont()` is not even asked when `CountFonts()` is 0.
- **Glyph names must exist** (the glyph set is read from `font.glyphs`); an unknown name gives that pair an `error` ("no glyph named 'Q'") and the other pairs are still read.
- **Text mode:** every character is mapped to the ONE glyph whose PRIMARY Unicode (`glyph.unicode`, plain int) is that code point; a character with no glyph, or with several glyphs (the reply lists up to 5), gives each pair it belongs to an `error`; glyphs whose Unicode could not be read are counted and named in the error ("no proof that none has it"). The neighbours of the text are the pairs (a text of n characters has n - 1 pairs, `chars` shows the two characters). Secondary Unicodes are not looked at.
- **Per pair:** `getter((left, right))` once; `None` -> `value 0`, `kerned false`; a finite number -> `value`, `kerned` = (`value != 0`); an exception, a bool, a string, NaN or infinity -> an `error` for that pair, **never a zero**.
- **Reply:** `open`, `mode` (`pairs` | `text`), `units_per_em` (from `font.info.unitsPerEm`, `null` unless a plain number), `count`, `errors`, `table_size` (= `len(font.kerning)` before the batch), `side_effect_detected` (table size before != after; `null` when a size could not be read), `results` (`left`, `right`, `chars` in text mode, `value`, `kerned` or `error`). Values come as floats (`-152.0`).
- **Transport facts (not limits chosen by us):** the listener's request head is read up to 65,536 bytes (a GET address is therefore limited to about that); a request BODY is read up to 1,000,000 bytes (roughly 30,000 pairs) and a larger one arrives cut off and answers 400 "not valid JSON"; every call runs on FontLab's main thread (QTimer-polled socket), so a very large read keeps FontLab busy while it runs. Real timings are NOT measured yet (K14).

**6. The product: server tool `get_kerning` (v0.30, v0.31), function `read_kerning(pairs, text, confirmed_large_read)`.**
- Signature `get_kerning(pairs: list[list[str]] | None = None, text: str | None = None, confirmed_large_read: bool | None = None)`. Exactly one of `pairs` / `text`. Validation happens BEFORE anything is sent (not even the version check): `pairs` a non-empty list or tuple of 2-element lists or tuples of strings matching `^[A-Za-z0-9._-]{1,63}$` after stripping; `text` a string of 2 or more characters without control characters; `confirmed_large_read` `None` or a real bool.
- **Approval threshold (v0.31, `_KERN_CONFIRM_ABOVE = 250`):** a request for MORE than 250 pairs (for text: more than 251 characters) with `confirmed_large_read` not exactly `True` is refused before sending, with the message "This request would read N kerning pairs, more than the 250-pair threshold, and nothing was read. Do NOT repeat the call yet. A large read costs many tokens: tell the person how many pairs you want to read and why, and ask whether they approve. Only after they have said yes, call get_kerning again with the same arguments and confirmed_large_read=true. Never set that flag without the person's approval." Name validation comes first, then the threshold. Exactly 250 pairs needs no approval; the flag on a small request is accepted and ignored. The flag is the agent's own claim: **a tool cannot verify that a human said yes** (decided and told to the user in the proposal).
- Then `_require_listener((0, 95), "get_kerning")` (an older listener is refused BEFORE sending; an unreadable version lets the call decide), then `POST /kerning/pairs` with `{"pairs": [[l, r], ...]}` or `{"text": "..."}` (the server always uses POST; the GET form of the listener is for browsers and PowerShell). Timeout `max(TIMEOUT_SECONDS, 5.0 + pairs / 100)` seconds (5.0 for a small read, 7.5 s for 250 pairs, 305 s for 30,000).
- Reply handling: `open` false -> the `NO_FONT` text; a listener `error` -> `ToolError("Kerning could not be read: ...")` (cut at 600 characters); `results` must be a list of exactly the expected length, otherwise "the listener's answer did not match the request"; every entry is rebuilt and type-checked: the echoed pair must equal the pair asked (else an error entry), an `error` text is kept (cut at 600), a `value` must be a finite non-bool number (else an error entry: "carried no usable number, so it was not read"), `kerned` is RECOMPUTED from the value (the listener's flag is not trusted), whole numbers become ints (`-152.0` -> `-152`, `-0.0` -> `0`), unknown fields are dropped. The server counts `errors` itself. `table_size` and `units_per_em` are forwarded only as plain numbers.
- Reply: `mode`, `units_per_em`, `table_size`, `count`, `errors`, `results`, `agent_instruction`, plus `side_effect_detected: true` (with a WARNING sentence in the instruction) only when the listener saw the table size change, and `large_read_confirmed: true` only after an approved large read. `agent_instruction` says: values are in font units (`units_per_em`), NEGATIVE = closer together, positive = apart; FontLab's own numbers including class kerning; `kerned: false` with 0 = FontLab has no kerning for that pair; a result with an `error` was NOT read and must never be treated as zero; feature-based (GPOS lookup), contextual and multi-master kerning are NOT covered; only the requested pairs were read, do not ask for the whole table; `table_size` 0 = the font has no kerning at all.
- **Pure read:** no `_note_change`, no `finish_changes`, no save (a static scan test checks the function source: no POST helper other than the read, no change tracking, no save).
- Tool docstring (tested for these phrases): "exactly one of", "Never ask for the whole kerning table: read only what the task needs", "There is no upper limit, but more than 250 pairs ... is refused until the PERSON has approved it", "Never set confirmed_large_read=true on your own", "Needs listener v0.95", "never a zero".

## 9. Two kerning tables and a name collision (2026-11-01, tests 168–176, listener 0.97, FontLab 8.9.5)

**Stage:** a new disposable font with glyphs `kn1L`, `kn1R`, `kn1S` (boxes, width 500), a right kerning class holding `kn1R` and `kn1S`, a class pair `kn1L : class` -100, and later an exception `kn1L : kn1R` -50, all made in FontLab's GUI. Rebuild recipe: [LIVE-TESTS.md](../LIVE-TESTS.md), after the K-series table. FontLab applied both values on screen (the boxes touch at -100; a 50-unit gap at -50).

**1. Where the kerning lives (probe 171, names only; tests 172–176).** `flPackage` has `kerning`, documented as `fgKerning kerning([string master_name])`, plus `masters` (`QList<string>`), `master` (string) and `getAllGroups()`, documented as `list((bool kernGroup, string groupName, int id, int mark, list(string glyphName)))` (the candidate source for P1.6). Not called: `getAllGroups`, `findGroup`, `kerningContainer`, and the writing members `autoKern`, `deleteGroups`. `flPackage.kerning("Regular")` returns an `fgKerning` that held the GUI's pairs (`len` 1, then 2 with the exception), while the legacy `font.kerning` stayed `len` 0 and answered `None`. Its `get` resolves classes like the legacy one (`kn1L:kn1S` -100 through the class). No read changed either table (`side_effect_detected` false).

**2. Defect A: `get_kerning` reads the wrong table for GUI-made kerning.** It reads `font.kerning`, so in this font it answered 0 / `kerned` false for both pairs and "table_size is 0: this font has no kerning at all" (169) while FontLab applied -100. Switching to the font window tab did not change it (170). For Arial, loaded from a file, the legacy table is filled and K2–K8 match the panel. Not known: whether a GUI edit made after a file is loaded reaches the legacy table, and which master the tool should read in a multi-master font.

**3. Defect B: a glyph name that is also a class name is read as the class.** FontLab names a new class after its first member (`kn1R`; Arial does the same: `v`, `Aring`, `e`). With the class named `kn1R`, `get(("kn1L", "kn1R"))` on the master's table returned the class value -100 although the exception -50 existed (`len` 2) and FontLab applied it (174). After renaming the class to `kn1grp` (the only change), the same call returned **-50** (176). So exceptions win when names are unambiguous (the K9 question), and `get` with a plain name tuple prefers a class of that name. Proven on the right side here and on the left side in test 195 (point 8). A class member without an exception is not affected (its class value is its real value). How a caller says "glyph": point 6.

**4. Panel facts.** An exception shows as a nested red row under its class pair; the footer counted 1 while the table held 2 entries (it counts top-level rows). "Show All Combinations" (panel menu) changed nothing visible in the panel.

**5. The probe** `GET /debug/trypkgkern?a=NAME&b=NAME[&master=NAME]&go=yes` (listener 0.97): the same one-font gate as `/debug/trysync`; the master must be one of `pkg.masters` (default `pkg.master`); 20 requests per listener run, counted before `pkg.kerning(master)`; calls only `pkg.masters`, `pkg.master`, `pkg.kerning(master)` once, and `len()` and `get((a, b))` once on each table. Stub cases 1230–1274; mutation run 31 of 32 killed (the survivor, `len()` returning a bool, is equivalent).

**6. Asking for a glyph or a group (tests 177–188, listener 0.98 to 0.100, the K9 font with the class named `kn1R`).**
- `fgKerningObjectPair` is not a name of the `fontlab` module (177). It lives in the loaded module `fontgate` (178, 180: `fgKerning`, `fgKerningGroups`, `fgKerningObject`, `fgKerningObjectPair`, `fgOpt_ExpandKerning`, `fgOpt_KerningOptions`); `type(font.kerning).__module__` reports `builtins` (179). Its docstring (181): `fgKerningObjectPair('nameLeft', 'nameRight', modeLeft, modeRight)` with `'glyphMode'` / `'groupMode'`.
- `get` REFUSES such a pair object (183, 185): *"Argument type must be Tuple(Tuple(string, bool), Tuple(string, bool)) or Tuple(string, string)!"*. The plain tuple repeated defect B (182: -100) and the class value for `kn1S` (184: -100).
- In `get(((a, flag), (b, flag)))` the flag means **"this name is a group"**: `((kn1L, False), (kn1R, False))` gave **-50**, the exception FontLab applies (186); `((kn1L, False), (kn1R, True))` gave -100, the class `kn1R` (187).
- `((kn1L, False), (kn1S, False))` gave **`None`** while FontLab applies -100 through the class (188): False / False matches only an exact glyph : glyph entry and does not resolve class membership.
- **Design consequence (not designed yet):** a correct read asks the exact glyph pair first and then resolves classes; when a name can collide with a class name, the tool needs the classes (`getAllGroups()`) or must mark the pair as unverified. Both open questions were answered later (point 8): the glyph : class exception wins, defect B occurs on the left side too, and the exact glyph pair misses a glyph : class exception.
- Probes: `/debug/moddir` (names only, loaded modules; v0.98) and `/debug/trypkgkern` `&mode=flags&flags=FF|FT|TF|TT` (v0.100; the v0.99 `mode=glyph` was removed).

**7. Both tables agree for a font loaded from a file (test 191, 2026-11-01, listener 0.102, FontLab 8.9.5, P0.8 step (a)).** Arial opened from the system, the only open font. `/debug/trypkgkern` (`mode=tuple`) on the 13 pairs of K2: the package has one master, `Regular` (the current one); `flPackage.kerning("Regular")` and the legacy `font.kerning` gave identical answers for all 13: -152 (A:V, V:A, Atilde:Ydieresis.c2sc), -227 (T:o), -76 (A:Wgrave.c2sc, Aacute:Wgrave.c2sc), -80 (A:Tbar.c2sc, Aacute:Tbar.c2sc), and `None` in both for A:B, Aacute:V, Adieresis:V, T:oacute, T:odieresis. `len` was 1370 in both tables before and after every read; no call errors, `side_effect_detected` false. Every value as predicted. ## 10. The fix (listener 0.104 / server 0.33, 2026-11-01, P0.8)

**How it reads.** `/kerning/pairs` reads `flPackage.kerning(current master)`, never the legacy `font.kerning` (defect A). Exactly one font must be open, so that the workspace's current package is the current font (stricter than before; until T5). A glyph's classes come from its `kerningLeft` / `kerningRight` group ids, named by ONE `getAllGroups()` per request when an id is not 0 (§9.9). Each pair is asked with explicit keys in FontLab's order, the first entry that exists answers: `((a,F),(b,F))`, `((a,F),(Rclass,T))`, `((Lclass,T),(b,F))`, `((Lclass,T),(Rclass,T))` (defect B: no plain name tuple is sent). Each result carries `source` (`glyph : glyph`, `glyph : class`, `class : glyph`, `class : class`, `none`) and the class names that answered; the reply carries `master` and `master_count`. An entry that holds 0 keeps its source; an unreadable, unlisted or twice-listed class id is an error for that pair. The server needs listener 0.104, checks every source and class name, and tells the agent to report the source and never guess. Timeout `5 + pairs/50` s.
