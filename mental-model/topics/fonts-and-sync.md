## 8k. Creating a new font (live-verified, listener 0.83 / 0.84)

**Question answered:** "Can an AI agent do the equivalent of File > New Font / Ctrl+N?" **Yes: construct `fontlab.flPackage()`.** The call itself registers the new font in the workspace; the GUI showed a font called "Unnamed Regular" as soon as the construct request returned (reported by the user). `flWorkspace.addPackage` is not needed (the `attach` stage exists but was never required). Nothing is written to disk.
**State of a brand-new font (read-only probes, live):** `CountFonts()` 0 -> 1, `packages` 0 -> 1, current package not null (`isNull` false); package `name` empty, `upm` 1000, `mastersCount` 1, `defaultMaster` `Regular`, `glyphsCount` 1, `path` empty, `fileName` "Unnamed Regular.xfo" (only a name), legacy `familyName` "Unnamed"; the only glyph is `.notdef`, EMPTY (0 layers, as in section 7). The new font became the current one (`CurrentFont()` reported family "Unnamed"). Nothing is saved by any tool (save policy: the person decides).
**Two fonts open (T5, tests 261–264, listener 0.111, 2026-11-03, read-only):** the workspace's current package has an EMPTY `name`, also for a saved font, so `name` cannot identify it. Its `path` can: the `.vfc` path of a saved font, the pseudo path `:/Arial: Normal` of a font opened from the system, equal to `CurrentFont().path` in every state seen. `fileName` ends in `.xfo` (`savedtestfont.xfo`, `Arial: Normal.xfo`), not in the file's extension. `flWorkspace.packages()` returns a `list` (2 entries); it was never iterated or indexed (unproven, [FONTLAB-API-RULES.md](../FONTLAB-API-RULES.md) §10). `CurrentFont()` and the current package both follow the font window in front: ONE click on the Arial tab switched both to Arial (263), ONE click back switched both back (264); Arial was listed first in the Fonts panel, so the font opened last does not decide. Not tested: two unsaved fonts (both paths empty), a font opened twice, the tools themselves.

**Several fonts open: what is known (2026-11-03, tests 262–284, listener 0.113 / server 0.39).** The goal is that every operation works with 2, 3 or more fonts open; one open font is required only where research shows it is the only way, and the person is then told so ([PROJECT.md](../PROJECT.md) goal 5, [DECISIONS.md](../DECISIONS.md)).
- **Proven live:** every reply that used a font names it, and a switched font window is reported in the next reply (269–272: no font, one font, two fonts in both directions; [server-and-endpoints.md](server-and-endpoints.md)); `fontlab_status` names the font in front (265); `get_kerning` reads the font in front, matched by path, names it, and refuses a new unsaved font in front (266–268, [kerning.md](kerning.md) §12). **Writes** (273–281, two saved fonts with the same family name, three window switches): `create_glyph`, `draw_polygon`, `set_glyph_width`, `set_glyph_sidebearings` and `set_glyph_unicode` changed only the font in front; the other font's glyph was absent there; drawings stayed `verified` across the switches, and `font.update()` in one font left the other font's drawing intact (280, 281); a same-name switch is reported as "another font with the same name … from a different file" ([LIVE-TESTS.md](../LIVE-TESTS.md) T5).
- **An error names the switch too** (fixed in server 0.39, live 282–284): in server 0.38 a failed first call after a switch carried no font fields while the server had already recorded the new font, so the switch was reported nowhere (277). Since 0.39 the error message ends with the `font_note`.
- **Two new unsaved fonts (285–290):** FontLab names the second new font "Unnamed1 Regular", so a switch between them is noticed by name although both keys are `none`; `create_glyph`, `draw_path` and `delete_glyph` changed only the font in front, and a read in the other font answered "No glyph named". The first glyph of a brand-new font could not be drawn while two fonts were open (288: the refusal below, seen live, nothing drawn); after the glyph was opened once in an editor tab it drew `verified` (288c).
- **Expected, not tested:** the read tools other than width and outline address the font in front through `CurrentFont()` as well. Known risks for writes: (1) a font window switched between two calls is reported in the next successful reply (since 0.113 / 0.38) but not prevented, so a write can still land in another font (an `expected_font` check is a candidate); (2) the modern-glyph cache and the guard's list of unsynced glyphs are kept for one font path at a time and cleared on a switch, so an unsynced glyph of font 1 (a failed sync, seen in stubs only) is forgotten after a switch to font 2 and back, and a later `create_glyph`, `delete_glyph` or `set_glyph_unicode` there could run `font.update()` over it; (3) two unsaved fonts share the empty path, so the cache, the guard and the once-per-font `.notdef` notice cannot tell them apart; (4) `finish_changes` counts changes across all fonts.
- **Needs exactly one open font today:** the first layer of a brand-new font (the layer name of `_package_layer_name`; refused with the reason otherwise, live 288); the font package's names for an UNSAVED font (`/font/current`, listener 0.118: matched by path otherwise, 301); the probes `/debug/trysync`, `/debug/trymodern`, `/debug/trypkgkern`, `/debug/trykerngroups`, `/debug/features`, `/debug/moddir?stage=kerntype`; `get_kerning` with a new unsaved font in front. None of these is yet shown to be a FontLab limitation.
- **Unknown, not unsafe:** everything not listed here. A case is tested before it is called safe or turned into a one-font requirement.
- **Practical rule until then:** reads and writes with several fonts open, without switching font windows during a task; after any switch, a `fontlab_status` call before the next write, because a switch is reported only in the reply after it, when a write has already landed.

**Font names (N1, tests 291–302, listener 0.115–0.118, 2026-11-03).** FontLab keeps the names Font Info shows in the font package: `psn` (PostScript), `ffn` (Full name), `tfn` (Family name), `tsn` (Style name), `sgn` (Style group) (299, 300). The legacy `font.info` can disagree: after the PostScript field was set to `W6aTest-Regular` in Font Info, `font.info.postscriptFontName` still read `Unnamed1-Regular` (298). For a font whose PostScript names were never set, they read as family and style joined (292). `font.info.dict` is an `fgFontInfoDict` (`flags`, `hinting`, `metrics`, `names`, `values`); `dict.names` (an `fgStringDict`) held 5 keys in a new font and 15 after Font Info's OK, never a PostScript key (297, 298), so it is not a "was this set" marker. Since listener 0.118 `/font/current` returns `package_names` when the package is matched to the font (302) and `package_names_unavailable` with the reason otherwise (301); server 0.41 reports the PostScript names from it ([DECISIONS.md](../DECISIONS.md), design C).

**"No font open" is `CountFonts() == 0`, NOT `CurrentFont() is None`:** with no font open `fl.CurrentFont()` still returns a placeholder legacy `fgFont` (empty path and family, one glyph named `Paper`). Until listener 0.104 the tools tested `CurrentFont() is None`, so with NO font open they answered as if a font were open (P0.2). **Fixed in listener 0.105:** every product route asks `_open_font()`, which treats `CountFonts() == 0` as no font; live: test 227 (the only font closed in a running FontLab). In a freshly started FontLab every read route answered `open: false` as well (test 244, K13); writes with no font open are stub-tested except one create (227). The gated probes use `CountFonts()` and refuse unless it is exactly 1.
**First glyph of a new font (listener 0.84):** `_derive_layer_name` normally reads the layer name from the font's other glyphs (section 8b); a new font has none (the `.notdef` has no layer). Fallback (`_package_layer_name`): the package's single master name, accepted only after strict checks: `CountFonts()` is the plain int 1, one package, a non-null current package, `mastersCount` exactly 1, `defaultMaster` equals `master` and the one name in `masters`, a text of 1 to 100 characters without a newline, the package's `glyphsCount` equals the font's glyph count and the package `upm` equals the font's `unitsPerEm`. Other glyphs' layers win when they exist; glyphs that disagree still REFUSE (the fallback never overrides a disagreement). Reply: `layer_name_source`. Live: the layer `Regular` was created and a polygon drawn into the first glyph. The gate tests (cases 760-787, 790-794) stub-cover every failed check.
**Not done / unknown:** no TOOL for creating a font (only the debug probe, once per listener run); setting family / style names (the `Info` class was only listed, never written); which font becomes current when TWO fonts are open (the probes refuse unless exactly one is open); what `fontlab_status` / `get_current_font` should say for a font with an empty path; saving the new font (deferred by the user).

**v10 additions to 8k:** re-confirmed in 139a: with no font open `CurrentFont()` is a placeholder `fgFont` (empty path and family, one glyph) while `CountFonts()` is 0; after `construct` the legacy family reads "Unnamed"; the first glyph's layer is `Regular` (`layer_name_source: "package master"`); drawing, sidebearings, width and the AUTO SYNC (8m) all work on such a font. Still no create-font tool.

## 8l. Unsynced layers and the update guard (live-proven in v0.84 to v0.86 sessions; guard in listener 0.87, server 0.27)

**v10 update (read 8m first):** the guard below is still in force, but since listener 0.89 the write tools sync a glyph themselves right after the write (`fontlab.Update(<flGlyph>)`), so the unsynced state normally lasts for milliseconds and the guard only acts after a FAILED sync. The statement below that "nothing syncs except editor-open + next request" is obsolete. The guard was verified live in v10 (139a / 139b: the unsynced drawing survived a create and `display_refresh: skipped` appeared; 142: no skip needed).

**Background (extends section 8i).** A layer made or changed through the modern API (`draw_polygon`, `draw_path`, width or sidebearing writes, automatic layer creation) exists only on the MODERN side. The legacy view of that glyph stays empty (legacy `layers` 0, `/glyph/outline` says `agree: false`, the grid tile stays blank) until FontLab "syncs" it.
**The data loss (live, one-variable runs, tests 126 to 134 of this session):**
- The legacy `font.update()` throws away EVERY unsynced layer in the font (129: two layers lost at once; the first-only / only-layer theory was refuted). It is called by `create_glyph`, `set_glyph_unicode` (together with `glyph.update()`), `delete_glyph` and the legacy width route. A drawing "disappears" with the next create.
- **133 (controlled):** `font.createGlyph(name)` ALONE keeps the layers; `createGlyph` + `font.update()` loses them. **134:** `set_glyph_unicode` (glyph.update + font.update) also wipes them.
- **Sync trigger (130 / 131):** opening a glyph in an editor tab (a GUI event) followed by the NEXT API request makes FontLab sync ALL glyphs (the grid tiles repainted when the next request ran, not at the GUI step). Layers synced this way survive creates even with the editor tab closed; layers drawn AFTER that sync are unsynced again.
- **Useless candidates (132, probe `/debug/trysync`):** `flPackage.update()` and `flWorkspace.instance().update()` both ran (return True) and changed nothing: outline still `agree: false`, tiles blank, `isChanged` false before and after; the next create still removed the layers.
- A pre-created glyph list does not protect either (pre-creating all glyphs first did not help).
**The guard (listener 0.87, section 12 for the tests).** Registry `_UNSYNCED` (per font key = `str(font.path)`, cap `_UNSYNCED_MAX` 500, an overflow flag). Registered by: `_modern_edit_target` when it creates a layer (`layer_created`), `draw_polygon` and `draw_path` when something changed, `set_glyph_width` (modern route, on success), `set_glyph_sidebearings` (on `changed`). The reply of those tools carries `synced_with_fontlab: false` and a `durability_note`.
**Before each legacy update call** (`create_glyph`, `delete_glyph`, `set_glyph_unicode` = `glyph.update()` + `font.update()`, `_set_width_legacy`) `_guard_decide(font)` classifies every remembered glyph (`_guard_classify`, read-only, never raises): `gone` (no such glyph any more) and `synced` are forgotten; `lost` (the modern wrapper reports no layer) is forgotten and REPORTED in `layers_missing_since_drawn`; `at_risk` = legacy `layers` 0, or legacy node count differs from the modern node count, or legacy `width` differs from modern `advanceWidth` by more than 0.01; `unknown` = any read fails (wrapper, layer, counts). `synced` needs legacy layers > 0, equal node counts and (when both readable) equal widths. If any glyph is `at_risk` or `unknown`, or the overflow flag is set, or the check itself fails, **the update calls are skipped** and the reply gets `display_refresh: "skipped"`, `display_refresh_skipped_to_protect` (names), `display_refresh_unreadable_glyphs`, `display_refresh_note`. The operation itself still runs (the new glyph is created, the codepoint set, the glyph deleted: all verified by the usual re-read). With nothing at risk the behaviour is exactly as in v0.86. The guard block never calls any update / save / export function (a static scan checks it). Delete: the check runs after `removeGlyph`, so a deleted unsynced glyph is `gone`.
**Known limits:** only glyphs changed through THIS listener run are remembered (a drawing made before a listener restart is unprotected); a glyph is forgotten only when a later guard check finds it synced, so a skipped refresh can last until the person opens a glyph in an editor and any request follows; `font.update()` was the only call proven harmful, the guard also skips `glyph.update()` in the two places that pair it with `font.update()`.
**Not yet proven live:** that the guard really keeps a drawing through a create in FontLab (the stub font WIPES unsynced layers in `update()` like FontLab does, so the stubs show it; the live run is test 136a / 136b, Appendix A); whether `set_glyph_unicode` on the unsynced drawn glyph ITSELF would lose it (the guard skips the update anyway); whether `font.update()` reverts a width or sidebearing edit on an already SYNCED glyph (the guard's width comparison treats a mismatch as at risk, untested live); whether File > Save / Save As keeps an unsynced drawing (test 135, DEFERRED by the user); whether the grid lists a plain-created glyph before a refresh (display refresh skipped).

## 8m. Automatic sync after modern writes (live-proven in the v10 session; listener 0.89, server 0.29)

**The question and the finding.** Sections 8i and 8l describe the root problem: a glyph written through the modern API (`flGlyph`) stays UNSYNCED, i.e. FontLab's legacy view (`fgGlyph`) does not follow, until FontLab "syncs" it. v9 knew one trigger only (open the glyph in an editor, then the next API request). **v10 found the direct call: `fontlab.Update(<flGlyph>)`.** The module function `Update` is documented by FontLab as "Update object and it's visual representations. Without argument update all changed objects. Update([fgGlyph|fgFont|flObject object])" (probe 138). Glyphbridge calls it with ONE argument, the modern glyph wrapper (the cached `flGlyph` of `_modern_wrapper`). **Never call it without an argument** (that updates ALL changed objects) and never `UpdateAll()`.

**Evidence (one variable per run; new unsaved "Unnamed Regular" font unless stated; each run started from a restarted listener because the probe allows one call per `how` per run):**
- **140a, `fillFgData(False, False)`** on the unsynced glyph: returned an object, changed NOTHING (verdict stayed `at_risk`, legacy layers 0, outline `agree: false`), no harm (`layer_lost` false). Useless.
- **140b, `Update(<flGlyph>)`:** verdict `at_risk` -> `synced` in one call; legacy layers 0 -> 1 (1 contour, 4 nodes); `layer_lost` false; the next `/glyph/outline` read the legacy side directly (`agree: true`, `margins_agree: true`). No editor tab, no GUI action. Return value `None`.
- **141, sidebearings:** polygon, then `set_glyph_sidebearings(20, 30)` (advance 450), THEN `Update`: legacy outline x 20..420, margins 20 / 30 / 450, `margins_agree: true`, no `modern_outline` needed. Then `create_glyph` (its legacy `font.update()` ran, nothing was at risk): the synced glyph kept outline, margins and advance. The grid tile of the glyph appeared after that later `font.update()` (the tile stayed BLANK right after `Update` alone in 140b: FontLab repaints its own screen at its own events).
- **142, v0.89 on a font OPENED FROM A FILE** (the local test font `savedtestfont.vfc`, 6 glyphs, layer `test_font`, layer name taken from the other glyphs): `create` stl88, `draw_polygon`, `set_glyph_sidebearings(20, 30)`, `set_glyph_width(520)` on the same glyph (second and third sync of the same glyph), `create` stl89, `draw_polygon` stl89, `create` stl90: EVERY write reply carried `synced_with_fontlab: true` and `fontlab_sync: {attempted: true, verdict: synced, synced: true}`; the later creates ran their legacy refresh (nothing skipped); stl88 kept outline x 20..420 and margins 20 / 100 / 520, stl89 its outline. Screenshot: grid with 9 glyphs, thumbnails of the two drawn glyphs repainted.
- **143 (read-only):** see 8o.

**How v0.89 works (listener).** `_guard_mark(font, name, how, result)` is the single hook every modern write tool already called (`draw_polygon`, `draw_path`, `set_glyph_width` modern route on success, `set_glyph_sidebearings` on `changed`). It registers the glyph (v0.87 behaviour), sets `synced_with_fontlab: false` + the unsynced `durability_note`, and then, if `_AUTO_SYNC` is true, calls `_auto_sync(font, name)`: gets the module function (`getattr(fontlab, "Update")`, must be callable), finds the glyph and its modern wrapper, calls `Update(w)` ONCE inside try/except, then `_guard_classify(font, name)`. Result block `fontlab_sync`: `attempted` (bool), `verdict` (`synced` | `at_risk` | `lost` | `gone` | `unknown`), `synced` (bool), `call_error` (text, only on an exception), `reason` (text, only when no attempt was made: no `Update`, glyph not found, wrapper unreachable). When `synced` is true: `synced_with_fontlab` becomes true, `durability_note` becomes `_SYNCED_NOTE`, the glyph leaves the registry. Everything is wrapped so `_guard_mark` NEVER raises and the reply is never lost. Not synced -> the v0.87 guard still protects the font (legacy update calls are skipped while anything is at risk). `_AUTO_SYNC = False` restores v0.88 behaviour exactly. The legacy width route (`legacy_empty_glyph`) is NOT synced by this (it already uses `glyph.update()`; it is not registered).
**Server v0.29:** `_add_guard_fields` forwards `fontlab_sync` (keys `attempted`, `synced` bools and `verdict`, `call_error`, `reason` non-empty texts; anything else dropped, a non-dict is ignored). Sentences in `agent_instruction`: nothing for a synced write; after an ATTEMPTED but failed sync "Glyphbridge asked FontLab to sync this glyph right after the change, but the glyph did not read as synced afterwards (see fontlab_sync.verdict and call_error)" followed by the old unsynced text (editor advice); not attempted -> only the old unsynced text. The old sentences are the last resort.
**Tests (sandbox; stubs):** listener cases 990-1008 (fakes for `Update`: syncs / no effect / raises / wipes / missing; `_AUTO_SYNC` off; polygon, path, sidebearings, modern width; legacy width route not synced; second edit of a synced glyph; create after a successful and after a failed sync; `_auto_sync` raising; two glyphs; no `UpdateAll`, no forbidden call, exactly one `upd(w)`, shipped default `True`; version) and server part 18 (18a to 18k). `m88_setup` (the `/debug/trymodern` tests) now sets `_AUTO_SYNC = False`, because those tests need a glyph that stays unsynced.

**Proven since (T3, tests 256–258, 2026-11-03):** a glyph whose editor tab is OPEN while the API writes its sidebearings (the original v0.24 defect scenario): with `Update` the next legacy read is fresh (x 20..420, `margins_agree` true, no `modern_outline`), the canvas moves the outline, and only the editor's metrics panel keeps the old numbers. **Proven since (T4, tests 145a–g, 259 and 260, 2026-11-03):** width and sidebearing writes on an EXISTING glyph with a legacy layer, `testglyph2` (a plain contour) and the Power Brush glyph `A` of a font opened from a file: each reply `synced: true`, the legacy width equal to the modern advance, `margins_agree` true, FontLab's bar equal to the reply (the whole-unit shift, into the element transform on `A`: [geometry.md](geometry.md) §8c). **What is NOT proven (scheduled, section 14):** multi-layer / multi-master glyphs (T7); a quadratic font (T8); time of `Update` on big glyphs (block LAST); File > Save / reopen after auto sync (deferred); `Update(<fgGlyph>)`, `UpdateAll()` and `prepareFontGateData(False)` were never tried live and need not be (the working call is found; they stay in the probe list). The failed-sync path (`verdict` not synced after an attempt) has only been seen in stubs.
**Facts to keep:** the number list of `updatedFgGlyphs()` is NOT a sync signal (ids appeared before and after the sync, 7 to 9 ids on a real font; the probe prints it as raw evidence only). `Update` returns `None`. The editor panel numbers and the info box of an already open editor tab still repaint only at FontLab's own events (8f); the DATA is synced regardless.

## 8f. GUI refresh facts (CLOSED; do not re-research)

FontLab repaints some GUI parts only on its own events. After an API write: the outline stroke usually repaints at once (`flWorkspace.instance().updateActiveViewport()`, called best-effort after every write; it repaints the stroke and sometimes the slider numbers, NOT the ghost fill); the editor panel numbers, the central info box, the grey ghost fill, the grid tile and the grid footer
lag until the user switches to the grid tab and back, or closes and reopens the glyph tab. A fresh glyph's grid tile stays BLANK until the glyph is opened; after opening, everything shows the right values (confirmed for width, sidebearings and the drawn outline). The editor's LSB/RSB numbers are cached per editor tab, so "the GUI did not change" proves nothing until the tab is reopened. Useless (all tried, live): `glyph.changed()`, `layer.changed()`, `shape.changed()`, `workspace.changed()`, `glyph.update()`, `flGlyph.updateSidebearings(True/False)` (returns False),
`updateActiveLayer`, `updateFgGlyph`, `layer.update`, `shape.update`; `blockUpdate` / `unblockUpdate` were deliberately never called. The write replies carry `display_refreshed` and a `display_note` that says all this to the person.
**Live end-to-end check (v0.75 / v0.22, last session):** a never-opened glyph went through `create_glyph` -> automatic layer creation -> `draw_polygon` -> `set_glyph_sidebearings` -> `get_glyph_outline`, and every step read back correctly; `ringtest` (square with a hole, sidebearings 40/60, advance 400) read back with 2 contours, 8 nodes, `verified`, outer counterclockwise, hole clockwise.

**v8 CORRECTIONS to 8f (live):** (1) 8f is about the GUI PANELS (editor panel numbers, info box, ghost fill, tile). The LEGACY READER that `get_glyph_outline` uses is a separate thing and is NOT refreshed by a plain grid-tab round trip (section 8i): it needed the editor tab to be closed and the glyph reopened. (2) "A fresh glyph's grid tile stays BLANK until the glyph is opened" is too strong: after the user closed another glyph's editor tab (landing on the grid), the tile of `ltr86o` (never opened) already showed the O with its empty counter. Probably the grid repaints on a tab switch; one sighting, the exact trigger is unknown. (3) After opening a glyph the editor shows the current numbers (confirmed again for `ltr86o`: 60 / 720 / 60 and the readout 660 / 516).
